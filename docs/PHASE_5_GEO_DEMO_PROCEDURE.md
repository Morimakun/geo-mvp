- **帳票上空欄は「0」とは区別する**
- 正解入力表では数値欄を空欄にし、メモ欄に「帳票上空欄」と記録

## デモの目的

ジオソリューションズ様に、以下を実演して説明すること：

1. **確認支援ツール** としての価値を理解してもらう
2. OCR誤読の補助的検出が可能であることを示す
3. 人間が最終確認できることを示す
4. 確認履歴が残されることを確認してもらう
5. 本格導入に向けた課題・要件を整理する

**重要:** 「自動確定ツール」ではなく「確認支援ツール」として説明  
**本番初期:** すべてのページで人間確認が必須（自動確定なし）

## P14の説明

### 画面で見せる部分

```
ページ: P14
v3値（標準版）: 34
v22値（V2.2）: 3
CSV値: 3
confidence: high
classification: auto_confirm_candidate
```

### 説明トーク

**背景:**
「v3という標準版のOCR読み取りでは『34』と読んでしまった件です。」

**価値:**
「でも、補助レイヤーV2.2では『3』と修正できて、CSVの『3』と一致しました。」

**見せ方:**
「このように、桁違いのOCR誤読を補助レイヤーで捕捉できるのが特徴です。」

**操作:**
「では、これを『確認済み』にしてみます。」

→ 「確認済み（V2.2を採用）」をクリック

**ログ確認:**
「確認ログが1件追加されました。」

ログの表示：
- timestamp: [現在時刻]
- page: P14
- user_action: confirm
- user_decision: accept_v22
- final_value: 3
- before_status: auto_confirm_candidate
- after_status: confirmed

**まとめ:**
「このように、人間が最終判定し、その履歴が確認ログに残ります。」

## P16の説明

### 画面で見せる部分

```
ページ: P16
v3値: 9
v22値: 2
CSV値: 11
confidence: low
classification: review_required
```

### 説明トーク

**背景:**
「P16は別の例です。v3が『9』、v22が『2』、CSVが『11』と、すべて異なります。」

**リスク:**
「しかも、V2.2の信頼度がlowになっています。」

**対応:**
「こういう場合は、自動確定ではなく『要確認』に分類します。」

**見せ方:**
「では、これを『保留』にしてから、後で『手動修正』するというフローを見てみます。」

### 操作1: 保留

→ 「保留」を選択

「保留」ボタンをクリック

**確認ログ確認:**
「確認ログが追加されました。」

ログの表示：
- page: P16
- user_action: defer
- user_decision: needs_follow_up
- before_status: review_required
- after_status: deferred

### 操作2: 手動修正（再度P16を選択）

→ 「手動修正」を選択

「操作記録」ボタンをクリック

**確認ログ確認:**

ログの表示：
- user_action: correct
- user_decision: manual_correct
- manual_correction_value: 11
- final_value: 11
- before_status: deferred
- after_status: corrected

**まとめ:**
「P16は『保留→修正』という流れでしたが、このように段階的に対応できます。」
「なぜ修正したかの理由も残ります。」
「すべての対応が追跡可能です。」

## 確認ログCSVの説明

### 見せる内容

ダウンロードしたCSVファイルを表計算ソフトで開く

「確認ログCSVには27個の項目が記録されます。」

**主要項目を説明:**

| 項目 | 意味 | 例 |
|-----|------|-----|
| log_id | ログの一意ID | LOG_20260608_120000_P14_confirm |
| timestamp | 確認した日時 | 2026-06-08T12:00:00+09:00 |
| page | ページ番号 | P14 |
| v3_value / v22_value / csv_value | 各源の値 | 34 / 3 / 3 |
| final_value | 最終値 | 3 |
| user_action | 実施した操作 | confirm, defer, correct など |
| user_decision | 判定内容 | accept_v22, needs_follow_up, manual_correct など |
| manual_correction_value | 手動修正の値（あれば） | 0, 11 など |
| decision_reason | 判定理由 | 自由テキスト |
| before_status / after_status | 状態遷移 | review_required → corrected など |

「このCSVをExcelで管理すれば、『誰が、いつ、どう対応したか』が全部残ります。」

## 想定質問と回答

### Q1: OCR精度は何％ですか？

**答え:**
「v3単体では、このカテゴリのデータで約50%の精度です。」
「V2.2を組み合わせると、高信頼度の確定候補が約57%に増えます。」
「ただし、精度そのものより『どの値が危ないか』を見分けることが重要です。」

### Q2: 完全自動化できますか？

**答え:**
「いいえ。このツールは『確認支援』です。」
「AIが『ここは危ないかも』と提示しますが、最終判定は必ず人間です。」
「むしろ誤確定を防ぐことが第一優先です。」

### Q3: CSVと違った場合はどうなりますか？

**答え:**
「『要確認』に分類されます。」
「人間が確認して、正しいほうを採用します。」
「修正理由も記録されるので、後から『なぜこの値にしたのか』が分かります。」

### Q4: AIが間違えた場合はどうなりますか？

**答え:**
「AIの提案を参考にしながら、人間が最終判定します。」
「手動修正機能があるので、AIと違う値に修正することもできます。」
「『AIの誤読を人間が直した』という履歴が確認ログに残ります。」

### Q5: 誰が確認したか残せますか？

**答え:**
「はい。確認ログにoperator_nameで『誰が』『いつ』を記録します。」
「現在のMVPは『確認者名』を入力欄で指定する形式です。」
「本格導入時には、認証連携で自動取得することも可能です。」

### Q6: Salesforceに自動反映できますか？

**答え:**
「現在のMVPでは、確認ログCSVを手動でExcelで管理する想定です。」
「本格導入時に、Salesforceへの自動反映も技術的には可能です。」
「ただし、誤確定防止の観点から『一度人間が確認した値』をSalesforceに反映するのが安全です。」

### Q7: 現場運用では誰が確認しますか？

**答え:**
「店舗側で確認する、または本社側で確認する、いずれでも対応できる設計です。」
「ただし、確認ログが残るので、『誰が何を判定したか』は明確になります。」

### Q8: 本格導入する場合、次に何が必要ですか？

**答え:**
「以下の3点を想定しています。」
「1. 実データでの検証（精度確認、実運用テスト）」
「2. Salesforce連携検討（自動更新するか、手動するか）」
「3. 確認者の認証・権限管理」

### Q9: 費用はどう考えますか？

**答え:**
「MVPは確認支援の仕組みを実装した状態です。」
「本格導入には、実運用テスト期間と、Salesforce連携実装などのカスタマイズが必要です。」
「詳細な仕様確定後に、改めてご提案させていただきたいと考えています。」

### Q10: この状態でどこまで業務削減できますか？

**答え:**
「初期段階では、確認が必要な件数を『事前に見分ける』ことで、確認作業の優先順位付けができます。」
「安全な自動確定候補を先に処理すれば、手作業を30～40%削減できる可能性があります。」
「ただし、実データで検証が必須です。」
