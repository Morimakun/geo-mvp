# Phase 5: 自動確定ロジック安全化設計（次フェーズへの提案）

**作成日**: 2026-06-09  
**対象**: ジオソリューションズ案件の本番導入前の安全化設計  
**重要度**: 🔴 **HIGH** - 誤確定防止が最優先

---

## 目的

PDF目視正解ベースの再評価により、現在の `auto_confirm_candidate` ロジックが**本番環境で使用不可**であることが判明しました。

本ドキュメントは、以下を達成するための設計方針を提示します：

1. **誤確定率を許容範囲まで削減**（目標: 5% 未満、理想: 1% 未満）
2. **確認支援としての実用性を確保**
3. **本番初期の安全な運用フロー**を定義
4. **段階的な信頼度向上**のロードマップを示す

---

## 現在の問題

### PDF目視正解ベースの評価結果（30ページ）

| 評価軸 | 数値 | 評価 |
|--------|------|------|
| **v3 精度** | 50% | v3 が最も正確 |
| **V2.2 精度** | 40% | 期待より低い |
| **CSV 精度** | 30% | 信頼できない |
| **auto_confirm_candidate 正解率** | **41.18%** | ❌ **不合格** |
| **危険誤確定率** | **58.82%** | ⚠️ **本番利用不可** |

### 危険誤確定の代表例

#### P30: 確認済みページでも誤確定

```
v3値:            2  ✓ 正確
V2.2値:          1  ❌ 誤り
CSV値:           1  ❌ 誤り
PDF目視正解:     2

auto_confirm_candidate = true  ← 危険！
confidence = high              ← 信頼度高いと判定しても誤り
```

**警告**: CSV と V2.2 が一致していても、PDF 原票と異なるケースがある

## なぜ auto_confirm_candidate をそのまま使えないか

### 1. **CSV 一致だけで確定していた**

```
問題のあるロジック:
├─ V2.2値 = CSV値
├─ confidence = high / medium
└─ → 自動確定候補 ✓

しかし:
├─ PDF 原票 ≠ CSV値（P30 など）
├─ PDF 原票 ≠ V2.2値
└─ → 誤確定 ❌
```

**改善必要**: CSV 一致を確定の十分条件に使うべきではない

### 2. **V2.2 の期待と現実のギャップ**

```
期待: V2.2補正により精度が向上
実現値: v3=50% > V2.2=40%

理由:
├─ P16: V2.2=2（不正確）vs v3=9（正確）
├─ P30: V2.2=1（不正確）vs v3=2（正確）
└─ P14: V2.2=3（正確）vs v3=34（計算誤り）
```

**改善必要**: V2.2 ベースの判定から v3 ベースへの見直し

### 3. **信頼度スコアだけでは不十分**

```
P30 の場合:
├─ confidence = high
├─ CSV 一致
└─ → auto_confirm = true

しかし PDF 目視では = 2 が正解
理由: 信頼度スコアは「AI が値を読み取れた確度」であり、
      「読み取った値が実際に正しい」とは無関係
```

**改善必要**: 「差分の大きさ」「複数ソース照合」などを追加ルール化

## 安全な判定方針（設計案）

### Tier 別の自動確定ポリシー

#### **Tier A: 自動確定可能（低リスク）**

条件:
```
1. v3 / V2.2 / CSV の 3値すべてが一致
2. confidence ≥ MEDIUM
3. 過去の誤確定実績がない項目
```

実装例:
```
if v3 == v22 == csv_value:
    if confidence >= MEDIUM:
        classification = "low_risk_auto_confirm"
    else:
        classification = "review_required"
else:
    classification = "review_required"  # デフォルト
```

期待される件数: 5～10 ページ（全30の約17～33%）  
危険誤確定率目標: ≤ 1%

---

#### **Tier B: 確認対象（中リスク）**

条件:
```
1. 3値のうち2値が一致している
2. ただしCSV一致だけで確定しない
3. 差分 = |max - min| < 3 の場合のみ軽微
```

実装例:
```
matching_count = sum([v3==csv, v22==csv, v3==v22, ...])

if matching_count == 2:
    diff = abs(v22 - v3)
    if diff < 3:
        classification = "confirm_low_priority"
    else:
        classification = "review_required"  # 差分が大きい
else:
    classification = "review_required"
```

期待される件数: 10～15 ページ  
対応: 優先度低く確認対象とする（自動確定しない）

---

#### **Tier C: 必ず確認（高リスク）**

条件:
```
1. 3値が不一致
2. 差分 ≥ 3 のページ
3. CSV値だけで自動確定したいページ
4. 過去に危険誤確定が実績のある項目
5. 手書き項目（信頼度が本質的に低い）
```

実装例:
```
if v3 != v22 != csv_value:
    classification = "review_required"  # 必ず確認
elif max(v3, v22, csv) - min(v3, v22, csv) >= 3:
    classification = "review_required"  # 差分が大きい
else:
    pass  # Tier A/B へ
```

期待される件数: 15～20 ページ  
対応: すべて人間で確認（自動確定しない）

---

### 本番初期の運用ルール（MVP）

```
┌─ 自動確定の実装 ─────────────────────────────┐
│                                              │
│ ✅ Tier A のみ自動確定候補として表示           │
│ ❌ 実際には自動確定しない（確認ログを必須）    │
│ ✅ Tier B / C は「確認対象」として色分け      │
│ ✅ すべてのページで「確認ログ」残す（監査用）  │
│                                              │
└─────────────────────────────────────────────┘

理由:
- 現在の auto_confirm は 58% 誤確定
- 100ページ以上のデータで再評価が必須
- 本番初期は「人間確認を自動化しない」設計が安全
- 確認ログにより、後で誤確定の実績を集計可能
```

## 低リスク候補の条件案

### **自動確定可能と判定する条件**

段階的なアプローチ:

#### **フェーズ 1（初期）: 最厳格**

```
auto_confirm = true ⟺ (v3 == v22 == csv) AND confidence==HIGH

期待: 3～5 ページのみ
危険誤確定率: 0%（目標）
```

#### **フェーズ 2（データ蓄積後）: やや緩和**

```
auto_confirm = true ⟺ (v3 == v22 == csv) AND confidence≥MEDIUM

期待: 5～10 ページ
危険誤確定率: <1%（許容）
追加条件: 過去100ページで誤確定実績がないこと
```

#### **フェーズ 3（安定化後）: 運用最適化**

```
auto_confirm = true ⟺ (v3 == v22 == csv) AND confidence≥MEDIUM
           OR (2値以上一致 AND 差分<2 AND confidence≥HIGH)

期待: 10～15 ページ
危険誤確定率: <2%（許容）
```

## 強制 review_required 条件案

以下のいずれかに該当する場合、**必ず review_required に分類**:

```
1. 3値が完全に異なる（v3 ≠ v22 ≠ csv）
2. 最大値と最小値の差が 3 以上
3. v3 と v22 の差が 5 以上（大幅補正）
4. CSV値が過去に誤確定実績のある項目と同じ
5. confidence = LOW のすべてのページ
6. 手書き項目（正の字など）
7. ブランク（空欄）の場合（0 との混同防止）
8. 過去のデータで「PDF目視と実際に不一致」が確認された項目
```

実装例:

```python
def classify_for_review(v3, v22, csv, confidence, field_type):
    """review_required に強制分類するロジック"""
    
    max_val = max(v3, v22, csv)
    min_val = min(v3, v22, csv)
    diff = max_val - min_val
    
    # 条件1: 3値が完全に異なる
    if v3 != v22 and v22 != csv and v3 != csv:
        return "review_required"
    
    # 条件2: 差分が3以上
    if diff >= 3:
        return "review_required"
    
    # 条件5: confidence=LOW
    if confidence == "LOW":
        return "review_required"
    
    # 条件6: 手書き項目
    if field_type in ["handwritten_tally", "manual_entry"]:
        return "review_required"
    
    return "candidate"  # Tier A/B へ進める
```

## P14/P16/P30 から見える教訓

### P14: V2.2 補正成功例（学習対象）

```
v3:            34 ← 計算誤り？
V2.2:           3 ✓
CSV:            3 ✓
PDF目視:        3 ✓

教訓:
├─ 3値一致 → 自動確定候補として OK
├─ v3 の外れ値にも対応可能（V2.2 で救済）
└─ confidence 高い場合、確認優先度を下げても安全
```

### P16: v3 が唯一の救済者（要反省）

```
v3:            9 ✓
V2.2:          2 ❌
CSV:          11 ❌
PDF目視:       9 ✓

教訓:
├─ V2.2 の低精度を証明（補正が逆効果になるケース）
├─ CSV の信頼性が低いことを証明
├─ v3 ベースでの再設計が必須
└─ 「V2.2 補正 = 改善」という仮説は誤り
```

### P30: 危険誤確定の警告（最重要）

```
v3:            2 ✓
V2.2:          1 ❌
CSV:           1 ❌
PDF目視:       2 ✓

auto_confirm_candidate = true  ← 人間確認済み後で不正確！

教訓:
├─ CSV一致 + confidence高 だけでは不足
├─ 人間確認済みページでも自動化は危険
├─ 「誤確定0」を設計上達成する必要がある
└─ 本番運用では「確認しない」は許されない
```

## 本番導入前の合格基準案

### 合格条件（いずれか一つを満たす）

#### **基準 A: 誤確定ゼロ（最も安全）**

```
条件:
├─ 100ページ以上のPDF目視正解データで検証
├─ 自動確定候補（auto_confirm=true）の全件が PDF目視と一致
├─ または、自動確定機能を無効化して運用
│  （すべてのページで人間確認ログを必須）

対応時期: 初期～6ヶ月
予定運用: 本番初期 MVP は「自動確定機能なし」で OK
```

#### **基準 B: 危険誤確定率 1% 未満（許容範囲）**

```
条件:
├─ 100ページ以上で検証
├─ auto_confirm_candidate 候補の 99% 以上が正確
├─ 誤確定しても「要確認」フラグで検出可能な構造

対応時期: 3～4ヶ月のデータ蓄積後
予定運用: 本番フェーズ2 で段階的に導入
```

#### **基準 C: 危険誤確定率 5% 以下（本番可)**

```
条件:
├─ 200ページ以上で検証
├─ auto_confirm 誤確定が複数回検出・修正された
├─ 誤確定パターンが特定でき、予防可能

対応時期: 6～12ヶ月の運用後
予定運用: 本番フェーズ3 で完全自動化を検討
```

## 結論と推奨事項

### **即座に実施すべき**

1. **本番初期は「自動確定機能を無効化」**
   - auto_confirm_candidate は表示されるが、確認は必須
   - すべてのページで確認ログを記録
   - 理由: 現在の 58% 誤確定率は本番利用不可

2. **「参考一致候補」への呼び名変更**
   - 「自動確定候補」という表現を避ける
   - 「確認の優先度が低い候補」との説明を徹底

3. **Tier A の条件を厳格化**
   - 3値一致 AND confidence=HIGH のみ
   - 期待: 3～5 ページ（全30の10～17%）のみ

### **本番初期（1～3ヶ月）**

- 全ページで確認ログを運用
- 誤確定パターンを収集
- 100ページ目処で再評価

### **本番フェーズ2（3～6ヶ月）**

- 基準 B（誤確定率 1% 未満）での自動確定候補導入
- 段階的に機能拡張
- ジオ様フィードバックを反映

### **本番フェーズ3（6～12ヶ月）**

- 基準 C（誤確定率 5% 以下）で完全自動化検討
- 項目別の最適ルール確立
