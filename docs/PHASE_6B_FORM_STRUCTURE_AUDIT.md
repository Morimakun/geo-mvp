## 監査の目的と背景

### 現状の課題

ユーザー提示画像により、以下の混同の可能性が判明：

1. **AI欄と非接列の混同**
   - Vision APIが読んだ「P14 AI=34」の出所が不明確
   - クロップ位置がAI欄でなく「非接」列を読んでいる可能性

2. **正の字の定義の揺らぎ**
   - 前回：「||||の本数」と説明
   - 今回：「書き順による1～5画」と修正
   - プロンプト改善前に統一が必須

3. **右側ブロック値の扱いの不確定性**
   - 0, 40, 15等がテンプレート値か実績値か不明確
   - 合計対象に含めるべきか不明

4. **使わない空欄の存在**
   - 帳票に「見えるが抽出対象ではない」欄がある可能性
   - クロップが隣接欄を拾うリスク

### 監査の重要性

プロンプト改善に進む前に帳票構造を正確に理解しないと：
- Vision APIへの指示が誤る
- crop座標の妥当性が検証できない
- 同じミスを繰り返す危険性がある

## 正の字カウント規則

### 正式定義

正の字は、**見た目の漢字名ではなく、書き順に沿った進行段階で判定する。**

```
書き順の進行：

1画目 ────   →  1画：横棒のみ  「一」形
         ↓
2画目 ───┼─  →  2画：横棒＋縦棒  「T」形
      または↑     （縦棒が突き抜けて十字形に見える場合も）
         ──┼──

3画目 ───┼─  →  3画：2画に加えて中段の横棒が追加
      ───┼───    「十」形 + 中段横棒
         ──┼──

4画目 ──┼──  →  4画：3画に加えて左側の縦棒が追加
      ──┼──      「井」形のような形
      ──┼──

5画目 ──┼──  →  5画：完成した「正」
      ──┼──
        └─┘
```

### 重要なルール

| 項目 | ルール | 例外・注意 |
|------|--------|----------|
| 見た目 vs 段階 | 見た目の漢字名ではなく、書き順の段階で判定 | 十字形に見えても2画の場合あり |
| 2画の形 | T字形が基本。縦棒が突き抜けて十字形に見える場合もある | どちらでも「2本の線」= 2画 |
| 3画の判定 | 2画に加えて「次の横棒」が追加された状態 | 十字形だけでは2画。横棒追加で3画 |
| 罫線・テンプレート線 | 数えない | セルの格子線を誤カウントしない |
| 複数行の合計 | 各行の正の字を合計して記入 | 例：1+2+1 = 4画 の場合、「4」と記入 |
| 0とblank | 別物として扱う | 0は記入、blank は非記入 |

### 画数判定の具体例

**以下のいずれかを確認：**

```
✅ 1画：   ─       （横棒1本のみ）
✅ 2画：  ─┼─      （横棒 + 縦棒。T形または十字形）
✅ 3画：  ─┼─      （十字形 + 中段横棒が追加）
         ─┼─
✅ 4画：  ─┼─      （3画に加えて左側縦棒）
         ─┼─
         ─┼─
✅ 5画：  ─┼─      （完成した「正」）
         ─┼─
        └─┘
```

## 誤解しやすいポイント

### 1. 十字形の判定

**❌ 誤り：** 十字形に見えたら「3画」  
**✅ 正解：** 十字形に見えても、線が「横棒＋縦棒」だけなら「2画」

**判定方法：** 線の本数ではなく、縦棒がどこまで書かれているかを確認  
- 縦棒が下まで貫通 → 「十」形 → 2画
- 中段に横棒が追加されている → 「十」形に横棒 → 3画

### 2. AI欄と非接列の混同

**❌ 誤り：** Vision APIが読んだ「34」は AI欄の正の字  
**✅ 現状：** 出所が不明確。AI欄か非接列かを確認が必要

**リスク：**
- クロップ座標がずれていると、隣の列を読んでしまう
- 非接列の複数行の正の字を「34」と誤読した可能性
- P14はこの混同の典型的な例

**対策：** P14のoriginal crop画像を確認して、Vision が実際に何を読んでいるか特定

### 3. 右側ブロック値の誤読

**❌ 誤り：** DL=0, DM=40, DP=0, DQ=15 を「スタッフが記入した値」と判定  
**✅ 正解：** テンプレート値。PDFに既に印字されている。Vision が読む必要なし

**リスク：**
- Vision が「40」を「実績値」と誤認して読む
- CSV の DL/DM/DP/DQ がテンプレート値と異なる場合、抽出値の信頼性が低下

**対策：** crop設定で右側ブロックを除外

### 4. 使わない空欄の混同

**❌ 誤り：** 見えている空欄 = 記入対象  
**✅ 正解：** 見えても使わない空欄がある可能性

**例：**
- 右側ブロック下の空欄（使わない）
- 将来用に予約された欄（使わない）
- セクション区切りの空行（使わない）

**リスク：** crop設定が「見えている範囲」で設定されると、使わない欄までも読まれる

### 5. 0と空欄の混同

**❌ 誤り：** 「0」と「空欄」を同じ意味で扱う  
**✅ 正解：** 異なる意味（0 = 記入、blank = 非記入）

**Vision API の現状：** P12 で混同が見られた

**対策：** プロンプトで「セルに何も見えない場合は『blank』と明示」

### 6. 合計欄の複数存在の混乱

**問題：** 以下の合計欄が異なる位置に存在
- AI（案件欄の合計）= 左側ブロック
- CZ（別カテゴリの合計）= 右側ブロック  
- 非接列の下部合計 = 別列

**リスク：** クロップ座標がずれると、異なる合計欄を読む可能性

### 7. PDF crop が隣接列を含むリスク

**問題：** Vision プロンプトで「AI欄を読む」と指示しても
- crop座標がずれていると隣の欄を読む
- 複数列を同時に視界に入れると混同する

**例：** AI欄を読むつもりが、非接列も同時に見えている

## AI欄・非接列・右側ブロックの関係

### 帳票上の位置関係

```
                    ┌──────────────┐
                    │   非接列     │
                    │  ────────    │  ← ユーザー画像で確認
                    │  正の字 |||  │
                    │  正の字 ||   │
                    │  正の字 |    │
                    │  ────────    │
                    │  合計  14    │  ← 下部合計
                    └──────────────┘

┌─────────────────────────────────────────┐
│  案件欄                  │  右側ブロック  │
│  AU / AV / AY / AZ / AI │ DL/DM/DP/DQ/CZ│
│   ↓   ↓   ↓   ↓  [合計] │ テンプレート値 │
└─────────────────────────────────────────┘
```

### 混同のメカニズム

**P14 の場合：**

1. Vision プロンプト：「AI欄を読む」
2. crop 座標が指定される
3. crop 画像の中に「非接列」も含まれている可能性 ← ⚠️
4. Vision が「非接列の複数行の正の字」を連結して「34」と読む
5. Vision が返す値：「34」

**検証が必要：**
- P14の original crop 画像に何が写っているか
- crop 座標の左右の幅
- 非接列が crop 範囲に含まれているか
