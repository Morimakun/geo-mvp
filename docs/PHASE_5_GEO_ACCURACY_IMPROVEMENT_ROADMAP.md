# Phase 5 - ジオソリューションズ向け 照合精度改善ロードマップ

**作成日:** 2026-06-08  
**対象:** 本格導入判断に向けた精度向上戦略  
**主眼:** 「誤確定防止」を最優先に、段階的に自動確定範囲を拡大する

---

## ⚠️ 重要な注記

本資料に記載する数値は、現時点では本格導入時の保証値ではなく、検証方針・評価基準案です。実際の精度は、ジオ様の実データ、FAX品質、記入状態、対象項目、運用条件により変動します。本格導入前に、実データを用いた項目別評価を行い、自動確定対象と要確認対象を切り分けます。

---

## はじめに：基本方針

### **精度向上の軸足は「削減率」ではなく「安全性」**

```
❌ 避けるべき思考
  └─ 「自動確定率 70% を 80% へ」

✅ 目指すべき思考
  └─ 「誤確定 0.5% から 0.1% へ」
     「要確認からの確認削減」
     「危険を確実に拾う」
```

---

## 第1章：精度指標の定義を分ける

### なぜ分けるのか

「OCR精度90%以上」という**一括の精度値は無意味**。以下の7軸で評価する。

---

### 1. PDF抽出精度

```
定義：
「PDFから対象セルをAIが読み取れた率」

例：
30ページ中、セル認識に成功した率
└─ AI合計欄セル特定：95%
└─ 内訳項目セル特定：90%
└─ 担当者欄：85%

測定方法：
target_cell_not_found フラグの反転
手動で数ページ確認して特定精度を推定

暫定評価：30ページ検証ベースの参考値。
実データ100ページ以上で再評価予定。
```

---

### 2. CSV候補特定精度

```
定義：
「CSVの該当する行・列を正しく特定できた率」

例：
30店舗分のCSV値が正しい行に紐付いた率
└─ store_code一致: 95%
└─ 日付一致: 92%
└─ 商品コード一致: 88%

測定方法：
store_code照合の一致率（既に実装）
日付・商品コード段階での一致率

暫定評価：30ページ検証ベースの参考値。
実データ100ページ以上で再評価予定。
```

---

### 3. 照合判定精度

```
定義：
「V2.2値とCSV値の対応が正しいか」

例：
V2.2=3 vs CSV=3 で「一致」と判定
V2.2=2 vs CSV=11 で「不一致」と判定
└─ 一致判定の正解率: 92%
└─ 不一致判定の正解率: 88%

測定方法：
人間が見直した「修正内容」から逆算
「V2.2が正しかった」vs「CSVが正しかった」の分布

暫定評価：30ページ検証ベースの参考値。
実データ100ページ以上で再評価予定。
```

---

### 4. 自動確定候補の正解率 ⭐ 最も重要

```
定義：
「auto_confirm_candidate と分類されたアイテムが、
 人間が『確認済み』と判定した率」

例：
100件の自動確定候補のうち
└─ 人間が確認して「OK」: 85件 → 正解率 85%
└─ 人間が「修正必要」: 15件 → 誤確定率 15%

暫定評価：30ページ検証ベースの参考値。実データ100ページ以上で再評価予定。
評価基準案：実データ検証で値を確定してから、本格導入判断の基準を設定します。
```

---

### 5. 要確認捕捉率 ⭐ 誤確定防止の関数

```
定義：
「実際に誤りがあるアイテムのうち、
 review_required に分類できた率」

例：
実際に人間が修正したアイテム 50件のうち
└─ 事前に review_required 分類: 45件 → 捕捉率 90%
└─ auto_confirm_candidate だったが誤り: 5件 → 漏捉率 10%

暫定評価：30ページ検証ベースの参考値。実データ100ページ以上で再評価予定。
評価基準案：漏捉率を許容範囲に抑えるための具体的な数値は、実データ検証後に確定します。
```

---

### 6. 危険誤確定率 ⭐⭐ 最優先

```
定義：
「人間が気づかずに自動確定が確定した、
 実は誤りだったアイテムの率」

例：
30ページの自動確定項目が本当に正しいか
人間が事後確認して「実は間違っていた」と判明
└─ 危険誤確定: 2件
└─ 危険誤確定率: 2/250 = 0.8%

現状値：未確定。実データ100ページ以上で評価予定。
評価基準案：業務影響が大きい項目（給与・評価）は0件を目指す。具体的な許容基準は実データ検証後に確定します。
```

---

### 7. 確認削減率

```
定義：
「自動確定候補により、確認作業が何%削減できるか」

例：
全250項目のうち
└─ auto_confirm_candidate: 170項目
└─ 確認削減率: 170/250 = 68%

ただし「確定したが実は誤り」があれば
その分の確認コストが後で増える。
└─ 誤確定対応コスト: +5〜10%
└─ 実質削減率: 68% - (誤確定2% × リスク) = 約 65%

暫定評価：30ページ検証ベースの参考値。実データ100ページ以上で再評価予定。
評価基準案：危険誤確定を抑えたうえで、確認削減率を段階的に高める。具体的な数値は実データ検証後に確定します。
```

```
──────┼──────────────────┼─────┼──────┼──────

```

## 第3章：最優先策の詳細（1位〜4位）

### 1位：異常値・範囲チェック ⭐⭐⭐

**効果:** 誤確定防止（低コスト）

**チェックロジック案:**

```python
# (1) 値が想定範囲外 → review_required
if not (0 <= v22_value <= 30):
    classification = "out_of_range"
    review_required = True
    review_reason = f"AI value {v22_value} is out of expected range [0-30]"

# (2) v3 との乖離が大きい（桁誤読の兆候） → review_required
v3_v22_ratio = abs(v22_value) / abs(v3_value) if v3_value != 0 else 0
if v3_v22_ratio > 5:  # 5倍以上の乖離
    review_required = True
    review_reason = f"Large discrepancy v3={v3_value} vs v22={v22_value}"

# (3) CSV一致でも confidence low なら → review_required
if matches_csv and confidence == "low":
    review_required = True
    review_reason = "CSV match but confidence is LOW"

# (4) ブランク判定なのに CSV が 1以上 → review_required
if blank_judgment and csv_value >= 1:
    review_required = True
    review_reason = f"Blank judgment but CSV={csv_value}"

# (5) 内訳検算が合わない → review_required
if sum_of_breakdown != v22_value:
    review_required = True
    review_reason = f"Breakdown sum {sum_of_breakdown} != AI {v22_value}"
```

**効果の推定（参考）:**
```
これらの改善効果は実装後、実データで検証します。
参考案としては：
└─ 異常値チェック導入で漏捉率が改善される可能性
└─ 危険誤確定を検出できる可能性
```

**実装コスト:** 1日程度

---

### 2位：照合スコアリング ⭐⭐⭐

**効果:** 「要確認の優先順位」を可視化

**スコアリング案（100点満点）:**

```
基本スコア:50点

✅ 加算 (positive signals):
  ├─ store_code一致         +30点
  ├─ 日付一致              +20点
  ├─ AI合計値あり          +15点
  ├─ CSV合計値あり         +15点
  ├─ v22とCSV一致          +15点
  ├─ confidence HIGH        +10点
  └─ v3とv22差分小(<1.5倍) +5点

❌ 減算 (negative signals):
  ├─ confidence LOW         -30点
  ├─ v3とv22差分大(>5倍)   -20点
  ├─ 値が範囲外            -50点
  ├─ 対象セル不明          -50点
  ├─ 内訳検算不一致        -25点
  ├─ blank判定             -20点
  └─ store_code不一致      -15点
```

**判定基準:**

```
80点以上  → auto_confirm_candidate
50-79点   → review_required (優先度=スコア)
49点以下  → high_risk_review / mismatch
```

**判定例:**

```
例1: P14
  store_code一致+30 日付一致+20 v22CSV一致+15 confidence HIGH+10
  = 75点 → review_required (優先度: 75)
  ※ただし既に auto_confirm_candidate なので無視

例2: P16
  store_code一致+30 日付一致+20 confidence LOW-30
  v3v22差分大-20 v22CSV不一致0
  = 0点 → high_risk_review (確実に要確認)

例3: P30修正後
  store_code一致+30 日付一致+20 v22CSV一致+15 confidence HIGH+10
  内訳検算一致+0
  = 75点 → review_required
  ※実は 0 に修正後は 85点になり auto_confirm_candidate へ
```

**実装コスト:** 2〜3日

---

### 3位：PDF内訳⇄合計の検算 ⭐⭐

**効果:** 「内部整合性チェック」で独立した検証軸

**実装イメージ:**

```python
# PDFから以下を抽出
breakdown_items = [
  {"item": "商品A", "value": 10},
  {"item": "商品B", "value": 2},
  {"item": "商品C", "value": 0},  # <- 0も取る
]

sum_of_breakdown = sum(item["value"] for item in breakdown_items)
ai_sum = 3  # V2.2が読み取った合計

if sum_of_breakdown == ai_sum:
    internal_check = "PASS"
else:
    internal_check = "FAIL"
    # csv_value との照合と独立した警告を発生
```

**効果:**
```
CSV完全依存を脱却
└─ 「V2.2=1, CSV=1 だが実は 0」というミスをも検出可能
```

**実装コスト:** 5〜7日（内訳セルの特定が複雑）

### 4位：マスタ整備 ⭐

**効果:** CSV照合エラーを減らす（確定率向上）

**必要マスタ:**

```
① 店舗マスタ
   ├─ 店舗名 → store_code（正規化）
   ├─ store_code → タブレット番号
   ├─ store_code → 担当者
   └─ store_code → 郵便番号・住所（PDF検証用）

② 担当者マスタ
   ├─ PDFに書かれた名前（手書き） → 正式表記
   └─ 正式表記 → 担当者ID

③ 項目マッピング
   ├─ PDF項目名 → CSV列名
   ├─ CSV列名 → 項目タイプ（金額/個数/比率）
   └─ 項目タイプ → 想定範囲

④ FAX機種・タブレットマスタ
   ├─ タブレット番号 → 画質特性
   ├─ 機種 → 典型的な誤読パターン
   └─ 店舗 → 過去の誤確定履歴
```

**実装コスト:** 10〜15日（マスタ構築・CSV取得）

## 第4章：確認ログの活用（改善サイクル）

### 確認ログから抽出すべき情報

```
① よくある誤読パターン
   └─ 「34と読まれやすい」「手書きが薄いと 0→1」
   └─ Few-shot プロンプト改善へ

② よく手動修正される項目
   └─ 内訳項目 → 画像前処理優先度を上げる
   └─ 担当者欄 → 手書き認識の限界を認識

③ auto_confirm_candidate が実は誤りだったケース
   └─ スコアリング基準の見直し
   └─ 新たなチェックロジック追加検討

④ review_required から confirmed へのケース
   └─ スコア境界値の最適化
   └─ 要確認必要度を再評価

⑤ 担当者別・店舗別の傾向
   └─ 「A店舗の修正率が特に高い」→ 画質問題?
   └─ 「B店舗は確認が早い」→ ノウハウ共有?

⑥ 確認削減効果
   └─ 「月100件のうち 60件が auto_confirm で
        実際の確認削減は 55 件（誤対応5件除く）
        → 実質削減率 55%」
```

### 確認ログ活用プロセス

```
毎週 / 毎月ごと：
  1. 確認ログを集計
  2. 誤確定・漏捉ケースを分析
  3. 新たなチェック必要性を判定
  4. 優先度リストを更新
  5. 次の改善ターゲットを決定
```

## 第5章：実データ検証計画

### 段階的検証フェーズ

```
Phase A: 30ページ検証（既に実施済み）
  └─ 精度指標の初期値取得
  └─ 主要な誤読パターンの確認
  └─ V2.2の妥当性確認

Phase B: 100ページ検証（本格導入判断前）
  └─ 精度指標を100ページで再確認
  └─ 誤確定率を評価
  └─ 店舗別・FAX品質別の分布確認

Phase C: 店舗別検証（パイロット3店舗）
  └─ 店舗ごとの確認削減効果測定
  └─ 実運用での操作性確認
  └─ 実際の業務削減時間を測定

Phase D: FAX品質別検証
  └─ 高品質FAX: 誤確定率を評価
  └─ 中品質FAX: 誤確定率を評価
  └─ 低品質FAX: 誤確定率を評価

Phase E: 手書き濃淡別検証
  └─ 濃い手書き: 精度を評価
  └─ 薄い手書き: 精度を評価
  └─ 薄い OR 不鮮明: review_required への分類を確認
```

### 各フェーズの検証項目

```
✅ CSV候補特定率
  └─ store_code一致で何%が正しく対応したか
  └─ 評価基準案：実データ検証後に設定

✅ 危険誤確定率
  └─ auto_confirm のうち実は誤りだった %
  └─ 評価基準案：業務影響を評価。実データ検証後に設定

✅ 要確認捕捉率
  └─ 実際に誤りだったもののうち、review_required に落ちた %
  └─ 評価基準案：実データ検証後に設定

✅ 確認削減率
  └─ 全項目のうち自動確定できた %
  └─ 評価基準案：危険誤確定を抑えたうえで段階的に評価。具体的な数値は実データ検証後に設定

✅ 確認時間削減効果
  └─ 1枚あたりの確認時間
  └─ 「手作業100%」vs「このツール」の比較
  └─ 評価基準案：実運用での削減効果を測定
```

## 第6章：やらないこと（スコープ外）

### ✅ 明示的に本格導入後に回すもの

```
❌ 完全自動化
   └─ 人間確認は必須。自動化率は 60～70% が上限

❌ Salesforce自動更新
   └─ 確認ログを経た「確認済み値」を反映すべき
   └─ 本格導入フェーズで別途検討

❌ case_items（個別商品）の自動確定
   └─ 現在は AI合計欄（合計値）のみ
   └─ case_items は複雑度が高く、別フェーズで

❌ Vision API の無制限再実行
   └─ 費用効率から現在の「1回実行」が最適
   └─ 複数回実行は Phase C 以後の判断

❌ v3プロンプト全面改変
   └─ 現在の v3 ロジックは堅牢
   └─ V2.2 を補助レイヤーとして使う設計を継続

❌ DB化
   └─ CSV + ログで運用可能
   └─ 本格導入後、ボリュームが月1万件超えたら検討

❌ 認証機能
   └─ 現在のローカル利用で問題ない
   └─ Salesforce連携時に統合認証を検討
```


### 本格導入判断への道筋

```
「今後のステップとしては、

 ① 100ページで精度検証
    └─ 危険誤確定率を評価

 ② パイロット3店舗で運用テスト
    └─ 実運用での確認削減効果を測定

 ③ その結果に基づいて『自動化範囲』を決定
    └─ これ以上の自動化はリスクが高い

    └─ 使うほど賢くなる

```

### 「削減率」ではなく「安全性」が軸

```
「最後に一つ大事なポイント。

 『自動確定率を 70% にできます』
 『確認が 60% 削減できます』

 という提案よりも、

 『誤確定を確実に防ぐ』
 『危険なものは確実に人間に回す』

 という提案が、給与・評価データを扱うジオ様には
 より重要だと考えています。

 そのため、本ロードマップは
 『誤確定防止を最優先』にした設計になっています。」
```

## 第8章：実装順序ガイド

### 本格導入判断が YES の場合

```
Q1. 危険誤確定率は許容範囲か？
    └─ YES → Q2へ
    └─ NO → Phase 6.5（異常値チェック導入）を先に実施

Q2. 確認削減率と誤確定防止のバランスは取れているか？
    └─ YES → Q3へ
    └─ NO → 現状で十分。本格導入判断可。

Q3. さらに精度向上を目指すか？
    └─ YES → ロードマップ優先度 1〜3 を段階的に実施
    └─ NO → 現状運用で 6ヶ月様子見 → 再評価

推奨実装順：
  1位: 異常値・範囲チェック（1週間）
  2位: 照合スコアリング（2週間）
  3位: 内訳⇄合計検算（1ヶ月）
  4位: マスタ整備（並行）
```

### 実装しない場合の代案

```
「完全自動化は難しいが、
 確認作業の『優先順位付け』だけでも
 相当な削減効果が見込めます。

 CSVベースの既存フローに対して
 『要確認をスコアで可視化する』
 だけでも、確認効率が向上します。」
```

---

## まとめ：精度改善のコアメッセージ

```
✅ DO:
  ├─ 誤確定防止を最優先
  ├─ 項目別・条件別に精度を評価
  ├─ スコアで要確認の優先度を可視化
  ├─ 確認ログを改善サイクルに活用
  └─ 実データ検証で段階的に拡大

❌ DON'T:
  ├─ 「削減率 90%」のような過度な期待
  ├─ 「完全自動化」目指し
  ├─ Vision API 無限実行
  ├─ 実データ検証なしでの拡大
  └─ 誤確定リスクの軽視
```

## 第9章：さらなる改善の前提条件

### 1. 正解データセット構築が最優先 ⭐⭐⭐

#### なぜ必要か

```
現在の精度評価は「30ページの肌感」です。
・自動確定候補の正解率 85-90%？ → 測る基盤がない
・危険誤確定率 0.8%？ → 人間が確認した「正解」がない

ここが曖昧なままだと：
  ① 改善施策が効いたかが判定できない
  ② スコアリング基準が信頼されない
  ③ 本格導入判断の根拠が弱い
```

#### 正解データセット（ゴールデンデータセット）とは

```
「業務専門家が確認して確定した値」を100ページ分（以上）保有する

以後のすべての改善は、このゴールデンデータに対して検証する
・異常値チェック導入 → 誤確定が何件減ったか
・スコアリング導入 → 要確認捕捉率がいくつになったか
・マスタ整備 → CSV候補特定率がいくつになったか

全部、ゴールデンデータに対して「Before / After」で測れる
```

#### 正解データセット構築フロー

```
Step 1: 100ページ抽出
  └─ 店舗別・FAX品質別・日付別にバランスしたサンプル

Step 2: 一次確認（ジオ様業務担当者 1名）
  └─ PDF と CSV を確認して「最も正しい値」を判定

Step 3: 二次確認（別の業務担当者 1名、または上司）
  └─ 一次との不一致があれば協議して最終確定

Step 4: 正解データ登録
  └─ page, store_code, field_code, final_judgment, error_type などを記録
  └─ 「このページのこの項目は、最終的に『3』が正解」という形で保有

Step 5: 以降の改善評価
  └─ 正解データに対して、各施策の効果を測定
```

詳細は [PHASE_5_GEO_GOLDEN_DATASET_SPEC.md](./PHASE_5_GEO_GOLDEN_DATASET_SPEC.md) を参照

### 2. 上流改善（帳票・入力方法）の可能性

#### 現状：誤読の大きな要因は AI ではなく「入口」

```
誤読分析から見えるパターン（推定）
  ├─ FAX画質：低品質FAXほどAI精度が落ちる
  ├─ 手書き：特に「濃淡」「字の大きさ」「正の字」が誤認しやすい
  └─ セル位置：PDFレイアウト変動で対象セルが特定できない

結論：AI を賢くするだけでなく、発生源を整えると精度が上がる可能性がある
```

#### 帳票改善案（将来施策）

```
将来、ジオ様側で帳票フォーマムを改善できる場合の参考案：

① 数字欄の改善
  ├─ 現状：罫線なし or 薄い罫線
  ├─ 改善案：枠付きマス（郵便番号形式）
  └─ 効果：セル認識精度が上がり、桁誤読が減る可能性

② チェック欄の改善（正の字カウント）
  ├─ 現状：「IIII」のような手書き正の字
  ├─ 改善案：チェックボックス化 or ラジオボタン化
  └─ 効果：手書き認識エラーが減る可能性

③ 記入欄の可視化
  ├─ 現状：記入欄が小さい or 枠がない
  ├─ 改善案：記入欄を大きく、濃い枠で囲む
  ├─ 指示：「濃く、大きく書いてください」と明記
  └─ 効果：FAX送信時の品質低下が軽減される可能性

④ 現行MVPでの対応
  └─ 帳票・Salesforce入力フローの変更は、本格導入時の追加施策として検討
  └─ 現時点で変更は提案しない
```

#### ジオ様と一緒に決めること

```
本格導入判断面談で、以下を相談対象に：

①「現行帳票でのAI精度向上」 vs 「帳票改善 + AI」のどちらを優先するか
②「すべての店舗」 vs 「試験的に1～2店舗」から始めるか
③「Salesforce入力も改善」するなら、どのタイミングか
```

### 3. エラー分類（Taxonomy）で改善ターゲットを明確化

#### なぜ必要か

```
「誤りが 20 件」では対策が見えません。
「誤りを分類して見える化」すると、投資先が判明します。

例：
  - 誤り 20 件のうち、14 件が「手書き不鮮明」なら
    → 帳票改善 / 画像前処理 に投資すべき
  - 誤り 20 件のうち、8 件が「対象セル誤認」なら
    → セルクロップ改善 / テンプレートマッチング に投資すべき
```

#### エラー分類体系案

```
誤りの種類                    改善方向
─────────────────────────────────────────
① 桁誤読                      異常値チェック / Few-shot改善
   (34→3など、数字を間違える)

② 手書き不鮮明               要確認分類 / 帳票改善 / 画像前処理
   (薄い手書きが読めない)

③ 正の字誤読                 チェックボックス化 / 手書き検出強化
   (正の字を別の数字に誤認)

④ 対象セル誤認               セルクロップ改善 / テンプレート調整
   (座標がズレて別セルを読む)

⑤ PDF画質不良                FAX品質チェック / 帳票改善
   (FAX送信時の品質低下)

⑥ CSV候補違い                マスタ整備 / スコアリング改善
   (複数のCSV行が合致)

⑦ マスタ不足                 マスタ拡充
   (店舗コード・日付などのマスタがない)

⑧ CSV側入力ミス              CSV側確認フロー整備
   (Salesforce側の入力が間違っている)

⑨ 人間確認ミス               確認UX改善 / 確認ガイドライン
   (AIは正しいが、人間が修正した)

⑩ 仕様未定義                 業務ルール確認
   (「どちらが正しいか」が決まっていない)
```

#### 正解データセットで集計する

```
100ページの正解データセットが完成したら、
各誤りを上記10分類に仕分けして集計

結果で以下が見える：
  - 「⑧CSV側入力ミス」が 60% なら → CSV側改善が重要
  - 「②手書き不鮮明」が 50% なら → 帳票改善が重要
  - 「③正の字誤読」が 40% なら → チェックボックス化が重要
```

### 4. Confidence 校正：モデルの信頼度を検証

#### 現状の課題

```
スコアリング案では：
  confidence HIGH    → +10点
  confidence LOW     → -30点

ただし、これは「AIが自分で『HIGH だと思う』」という申告です。
実際に正しいかは未検証。
```

#### Confidence校正の必要性

```
例１：confidence が HIGH でも 30% 外れるなら
  → 「HIGH だから自動確定」という設計は危険

例２：confidence が LOW でも 80% 正しいなら
  → 「LOW だから要確認」は過度な分類で、スコアリングの他の要素で判定可

つまり、confidence の「本当の有効性」を測って、
スコアリング加点・減点を再調整する必要がある
```

#### 校正フロー

```
Step 1: 正解データセット 100ページを confidence 別に分類
  └─ HIGH グループ、MEDIUM グループ、LOW グループ に分ける

Step 2: 各グループの正解率を測定
  ├─ HIGH グループの正解率：○%
  ├─ MEDIUM グループの正解率：○%
  └─ LOW グループの正解率：○%

Step 3: 結果に基づいてスコア加点を調整
  ├─ HIGH グループが 95% 正しい → +10点 は正当
  ├─ LOW グループが 70% 正しい → -30点 は過度 → -15点 に修正
  └─ MEDIUM グループの有効性を測って、加減点を設計

Step 4: 修正したスコアリングで再評価
  └─ 新しいスコアリング ＋ confidence校正 で精度がどう変わるか
```

### 5. 異種モデルクロスチェック（将来施策）

#### 同一モデル複数回実行の限界

```
現在の「複数回AI実行で信頼度実測」の案は、同じモデルを複数回実行する

ただし：
  - 同じモデルは同じ間違い方をする
  - ばらつきは小さく、「本当は間違っているが、毎回一致」という罠がある
```

#### 異種モデルとの組み合わせ

```
例：同じページを「Claude Vision API」「GPT-4 Vision」「Cloud Vision」に投げる

もし 3 つ全部「3」と言ったら、信頼度が非常に高い
もし 「Claude=3」「GPT=11」「Cloud=?」と割れたら、review_required に落とす

効果：
  - 独立した複数系統で「本当に安全か」を検証
  - 誤確定防止に効果的

課題：
  - APIコスト3倍
  - 処理時間が長くなる

運用案：
  - 全件ではなく「要確認ケース」「自動確定候補（LOW信頼度）」に限定
  - 本格導入での追加施策として検討
  - 現行MVPでは実装しない
```

### 6. 確認UX改善：人＋AIの最終精度を高める

#### 最終精度 = AI精度 × 人間の確認品質

```
AI が「高精度」でも、確認者が疲れて見落とせば誤確定が出ます

最終的な信頼性は：
  AI 部分（今までのロードマップ）
    + 人間が見やすく、判定しやすいUI
    = 最終精度
```

#### 確認UX改善案（本格導入時の候補）

```
① 値の横に「対象セル画像」を表示
  ├─ 現状：AI値の数字だけ
  ├─ 改善案：PDF上の該当セルを自動クロップして表示
  └─ 効果：確認者が目視で値を確認でき、読み落としが減る

② 危険度順に並べ替え
  ├─ 現状：ページ順 or ランダム
  ├─ 改善案：スコアが低い案件（危険度高）を上に表示
  └─ 効果：集中力が高い最初に危険案件を処理でき、確認精度が上がる

③ キーボードショートカット
  ├─ 現状：マウスでボタンクリック
  ├─ 改善案：「Y キー=確定」「N キー=要確認」など
  └─ 効果：確認速度が上がり、疲労軽減→確認精度向上

④ 確認理由入力の簡略化
  ├─ 現状：フリーテキスト入力
  ├─ 改善案：「確定」「保留」「修正」のラジオボタン＋プルダウン
  └─ 効果：入力速度アップ＋理由の標準化

⑤ 状態表示の視認性
  ├─ 現状：「auto_confirm / review_required」だけ
  ├─ 改善案：色分け（緑=確定、黄=保留、赤=修正）
  └─ 効果：ひと目で「どの案件の状態か」が分かり、確認ミスが減る
```

#### 現行MVPでの対応

```
大規模UI改善は本格導入時の施策として扱う

現在は：
  - 確認UI は機能的に実装済み（P14/P16/P30 が操作可能）
  - ただし「見やすさ」「速さ」の最適化は未実施

本格導入時に：
  - ジオ様の実運用フィードバック を受ける
  - その後、UX改善を段階的に実装
```

### 7. 本格導入判断時にジオ様と一緒に決める事項

#### A. 正解データセット構築の実行時期・方法

```
□ いつから 100ページの正解データ構築を始めるか
□ 誰が一次確認・二次確認を担当するか（社内？外部委託？）
□ サンプル抽出の方針（どの店舗・FAX品質・日付から選ぶか）
□ 確認期間はどのくらい見積もるか（1ヶ月？2ヶ月？）
```

#### B. 帳票改善の判断

```
□「現行帳票で精度向上を目指す」vs「帳票改善 + AI」の選択
□ 帳票改善するなら、どの要素から着手するか（数字欄？チェック欄？）
□ 改善は全店舗か、試験店舗か
□ 帳票デザイン・運用方針の変更は誰が決定するか
```

#### C. エラー分類と改善優先度

```
□ 正解データセット完成後、エラー分類を共有
□「手書き不鮮明」が多いなら帳票改善を優先、など
□ 改善施策の優先順位を、ジオ様とのデータ共有で決定
```

#### D. Confidence校正のアクション

```
□ 100ページ正解データの confidence 別正解率を測定
□ 結果に基づいてスコアリング基準を修正するか判断
□ 修正したスコアリングで確認削減率がどう変わるか検証
```

#### E. 異種モデルクロスチェックの検討

```
□ API コスト vs 誤確定防止の効果 をどう判断するか
□ 要確認ケースのみ複数モデル併用 の方式で妥当か
□ 導入の時期（本格導入直後か、半年後か）
```

#### F. 確認UX改善のロードマップ

```
□ 本格導入後の「見やすさ改善」を誰が実施するか
□ ジオ様からのフィードバック を月 1 回などで収集する機会を設ける
□ 高優先度の UI改善（例：対象セル画像表示）から段階的に実施
```

### まとめ：本格導入への段階的改善

```
今：MVP デモ（確認支援の実証）
  ↓
本格導入判断 ← このタイミングで 7 つの事項を協議
  ↓
正解データセット構築（1～2ヶ月）
  ┌─ ゴールデンデータセット完成
  ├─ エラー分類集計 → 投資先を明確化
  ├─ Confidence 校正 → スコアリング精度向上
  └─ 改善施策の優先度が見える化
  ↓
段階的改善実装（スコアリング → 異常値チェック → マスタ整備 など）
  ↓
本格化・全店舗展開
```
