「AI合計欄」の "AI" は **人工知能ではなく、帳票上の項目名** です。（おそらく「紹介（Au）・その他（Ay）・その他（Az）」の合計、あるいは別の意味）

```

したがって、まずは AI合計欄を監査することで、
システム全体の信頼性を測ることができる
```

## 📊 **何が起きているのか**

### 仮説1：GT誤り仮説（却下される可能性が高い）

```
もし疑惑ページの初期GT値が誤りなら：
  ↓ 人間確認で修正
  ↓ スコアが大きく変わるはず
  
実際：スコア不変
  → GT誤り仮説は**限定的**
```

### 仮説2：項目対応ズレ（新仮説・最有力）

```
v3 / V2.2 / CSV が見ている「AI合計欄」と
PDF帳票の「AI合計欄」が実は異なる領域かもしれない

例：
  - PDF上: AI欄 = ページ左上の「正の字」記入欄
  - CSV列: AI欄 = 別の位置の「数字合計」欄
  
この場合、3ソースが一致していても、
PDF原票の「正しいAI欄」とは無関係の値になる
```

## 🔎 **次に疑うべきこと**

### 1. **Crop位置**（最優先）

```
v3/V2.2 が使用している case_items 領域:
  bounds = (top 12%, bottom 24%, left 0%, right 45%)

この領域に、複数のセル（AU/AV/AY/AZ/AI）が含まれている。

可能性：
  → AI欄の切り出し位置が誤って、隣のセル(AZ)を含めている
  → または別の位置を見ている
```

**検証方法**: P21（候補0 vs 3ソース3）の full_page 画像で、
crop box がどこまで含まれているか目視確認。

### 2. **PDF項目名とCSV列の対応**

```
CSV列35 = "AI" は、PDF帳票のどこを指すのか？

可能性：
  → 帳票の「AI合計欄」（正の字が書かれる欄）ではなく、
     別の集計列 or 異なるセルを指しているかもしれない
```

**検証方法**: Salesforce CSV の列35 定義を確認。
PDF帳票上でCSVの値がどこから来ているか、ドキュメント追跡。

### 3. **正の字欄と数字合計欄の扱い**

```
PDF帳票上には：
  - 「正の字」を手書きする欄
  - その下に「合計数字」を記入する欄
  
2つが存在する可能性。

v3/V2.2/CSV が見ているのはどちらか？
PDF原票の「正解」はどちらか？
```

**根拠**: P10/P2 で「正の字で記入」という注記がついた。
他のページではなぜ数字なのか、その理由が不明。

### 4. **CSV列35=AI の定義**

```
Salesforce 側の「AI列」が、
実際にどのセルからデータを取得しているのか、
ドキュメントで確認する必要あり。
```

### 5. **v3/V2.2 が同じ領域を見ている可能性**

```
V2.2 は v3 の誤読を「補正」するはずだが、
実は「同じ誤った領域から」データを取っている可能性。

V2.2 のプロンプトで、
領域の再指定や独立した crop を使用しているか確認。
```

## 📊 **次フェーズのロードマップ**

### Phase 2: 項目対応・crop位置・CSV列対応の精査

1. crop box を P21（候補0 vs 3ソース3）で直視確認
2. Salesforce CSV 列35 の定義をドキュメント調査
3. PDF帳票の項目名・欄の位置をマッピング表で整理
4. v3/V2.2 のプロンプト・crop 設定を再確認

### Phase 3: 確認後のTier設計

項目対応が明確になった後、低リスク Tier を設計：

```
Tier A（完全信頼）:
  = v3 / V2.2 / CSV の項目対応が確認でき、
    かつ 3ソース一致している場合 → 自動確定候補

Tier B（要確認）:
  = ソース間で不一致、または項目対応に曖昧さがある場合
    → 必ず人間確認

Tier C（常に確認）:
  = 手書き正の字など定義が不明な場合
    → 自動化しない
```

---

**結論**: GT監査により、「単なる精度低下」ではなく「項目定義・対応の確認が本質的に必要」という、より重要な課題が露呈しました。これは本番環境の信頼性向上につながります。
