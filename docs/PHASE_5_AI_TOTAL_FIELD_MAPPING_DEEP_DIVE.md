# Phase 5 Deep Dive: AI合計欄の項目対応ズレ検証

**作成日**: 2026-06-10（Phase 2）  
**状態**: 重大な項目対応ズレを確認  
**結論**: 「OCR精度」の問題ではなく「項目定義・対応ズレ」が本質的な課題

---

## 目的

Phase 1 のPDF目視確認により、v3/V2.2/CSVが同じ値でもPDF原票のAI合計欄とは異なるケースが13ページで確認されました。

本Phase では、その原因が何かを特定することを目的とします。

---

## 🔍 **前提：「AI」は人工知能ではなく帳票項目名**

「AI合計欄」の **"AI"**:
- ❌ Artificial Intelligence（人工知能）ではない
- ✅ **帳票上の項目名**（おそらく「紹介（Au）・その他（Ay）・その他（Az）」の頭文字か、別の意味）

したがって、本レポートは「AI抽出精度」ではなく「**帳票項目とのマッピング問題**」を扱っています。

---

## 現在の問題構造

### これまでわかったこと

1. **v3/V2.2/CSVが同じ値を出している** — 3ソースが独立していない、または同じ「定義ズレ」を共有している
2. **その値が PDF原票と異なる** — 目視確認で確認済み
3. **スコアが変わらない** — GT監査でもスコア不変＝項目対応ズレが本質

### 疑うべき原因（優先度順）

#### **1️⃣ CSV列35の定義ズレ（最有力）**

| 項目 | 内容 |
|------|------|
| **CSV列35のヘッダー** | **「紹介総数」** |
| **意味** | リソース導入情報の集計数（導入物件・ユーザーに関する指標） |
| **PDF「AI合計欄」** | 正の字で記入される項目？ or 別の数字合計欄？ |

**結論**: CSV列35「紹介総数」とPDF帳票の「AI合計欄」は**全く別の意味**の可能性が極めて高い。

#### **2️⃣ Crop位置のズレ**

現在のcrop bounds:
```
(top=12%, bottom=24%, left=0%, right=45%)
```

可能性:
- case_items 領域の定義が正しくない
- 隣接セルを含めている
- 実際のAI合計欄とは異なる位置を切っている

**検証方法**: `{ページ}_ai_total_region_overlay.png` で赤枠を視確認

#### **3️⃣ 正の字欄と数字合計欄の混同**

PDF帳票上には2つが存在する可能性：
- 「正の字」を手書きする欄（P10/P2で「正の字で記入」と記注）
- その下に「合計数字」を記入する欄

v3/V2.2/CSVが見ているのはどちらか、PDF「AI合計欄」としての正解はどちらか、が不明。

#### **4️⃣ PDFページとCSV行の対応ズレ**

PDFページ番号（P1-P30）と、CSVの行番号が正しく対応しているか不明。
対応ズレがあると、「正しく見えている値」が「誤った行」と照合される。

## 🔴 **重大な発見：3ソース一致でもPDF目視と相反する**

### データ分析結果

**3ソース完全一致のページ**: 15ページ（P1, P5, P7, P8, P9, P10, P13, P18, P19, P21, P22, P23, P25, P26, P27）

**うち、PDF目視と不一致**: **全部15ページ**

```
P21: 3ソース値=3 vs PDF目視=0  （差=-3）
P25: 3ソース値=3 vs PDF目視=0  （差=-3）
P27: 3ソース値=0 vs PDF目視=4  （差=+4）
P23: 3ソース値=1 vs PDF目視=4  （差=+3）
P26: 3ソース値=2 vs PDF目視=5  （差=+3）
P19: 3ソース値=2 vs PDF目視=4  （差=+2）
P10: 3ソース値=0 vs PDF目視=2  （差=+2）
P18: 3ソース値=1 vs PDF目視=2  （差=+1）
P22: 3ソース値=2 vs PDF目視=1  （差=-1）
... etc
```

### 解釈

```
1. v3/V2.2/CSVが同じ値で一致している
   ↓
2. それは「3つが合意している」のではなく「3つが同じズレを共有している」
   ↓
3. つまり、項目定義 or 領域定義が根本的にズレている
```

**正常な状態であれば**: 3ソースが一致 → PDF目視とも一致（一部のばらつき除き）

**実際**: 3ソース一致 → 常にPDF目視と不一致

→ **これは「精度の問題」ではなく「定義のズレ」**

---

## 📊 **CSV列35「紹介総数」の定義確認**

### ヘッダー周辺

| 列 | ヘッダー | 意味 |
|----|---------|------|
| 30 | ⑮導入物件数（MT） | リソース導入関連 |
| 31 | ⑯未利用者数（MT） | リソース導入関連 |
| 32 | ⑰引越予定ユーザー数（MT） | リソース導入関連 |
| 33 | ⑱未導入物件数（MT） | リソース導入関連 |
| 34 | ⑲ヒアリング不可 or 不明 | リソース導入関連 |
| **35** | **「紹介総数」** | **リソース導入・紹介に関する指標** |
| 36 | 新規紹介総数 | リソース導入・紹介関連 |

### 結論

CSV列35「紹介総数」は、**リソース導入情報の集計数**であり、

PDF帳票上の「AI合計欄」（正の字で記入される欄のようなもの）とは**全く別の意味**。

## 📋 **本質的な課題**

```
OCR精度 50% ← これは「症状」
  ↓
v3/V2.2/CSVが同じ値を出す ← これは「根本原因のヒント」
  ↓
その値がPDF目視と相反 ← これが「本質」
  ↓
項目定義・対応ズレ ← これが「真の原因」
  ├ CSV列35が違う意味
  ├ Crop位置がズレている
  ├ 正の字/数字欄の定義が不明
  └ PDFとCSVの対応がズレている
```

**改善戦略**: 精度を上げるのではなく、**定義を明確にする**
