## P14説明トーク（3分）

### セットアップ

「では、具体例を見てみましょう。」

「P14というページです。」

「画面を見ると、

```
v3値（標準版）: 34
v22値（V2.2）: 3
CSV値: 3
confidence: high
classification: auto_confirm_candidate
```

という状態です。」

### 背景説明

「v3という標準版のOCR読み取りでは『34』と読んでしまいました。」

「でも、補助レイヤーV2.2では『3』と補正できます。」

「そして、Salesforceの『3』と一致しました。」

### 価値説明

「このような、いわゆる『桁違い』のOCR誤読を補助レイヤーで検出できるのが特徴です。」

「これはFAX品質のバラつきや、手書き形式の違いに対応するためです。」

### 操作・ログ確認

「では、これを『確認済み』にしてみます。」

[→確認済み ボタンをクリック]

「確認ログが1件追加されました。」

「見ていただくと、以下のように記録されています：

```
timestamp: 2026-06-08 14:32:45+09:00
page: P14
user_action: confirm
user_decision: accept_v22
final_value: 3
before_status: auto_confirm_candidate
after_status: confirmed
decision_reason: AI V2.2は3で正しい。OCR誤読を補正。
```

」

### まとめ

「つまり、人間が『この値でいい』と確認し、その履歴が確認ログに残ったということです。」

「誰が確認したか、いつ確認したか、何を理由に確認したか、全部残ります。」

## P16説明トーク（5分）

### セットアップ

「次にP16の例です。こちらは『要確認』という判定です。」

「画面を見ると、

```
v3値: 9
v22値: 2
CSV値: 11
confidence: low
classification: review_required
```

という状態です。」

### 背景説明

「v3が『9』、v22が『2』、CSVが『11』と、すべて異なります。」

「しかも、V2.2の信頼度（confidence）が『low』になっています。」

「『confidence が low』というのは『このAI値は信じにくいかもしれない』ということです。」

### 対応方針

「こういう場合、自動確定ではなく『要確認』に分類します。」

「『要確認』は『ここは人間で見たほうがいい』というサインです。」

「では、このアイテムがどういう対応フローになるか見てみましょう。」

### 操作1：保留

「まず『保留』にしてみます。」

[→保留 ボタンをクリック]

「『保留』というのは『今すぐ判定しない。後で改めて確認する』ということです。」

「確認ログに以下が記録されました：

```
user_action: defer
user_decision: needs_follow_up
before_status: review_required
after_status: deferred
```

」

「『需要フォローアップが必要』『状態は保留』と記録されています。」

### 操作2：手動修正（後フェーズ）

「では、その後、確認が進んで『修正が必要』と判定した場合のフローです。」

「P16を再度選択します。」

「今度は『手動修正』を選択します。」

[→手動修正 選択]

「修正値を『11』に入力します。」

「理由は『CSVとPDFを確認し、最終値は11と判断』と入力します。」

[→操作記録 ボタンをクリック]

「新しいログが記録されました：

```
user_action: correct
user_decision: manual_correct
manual_correction_value: 11
final_value: 11
before_status: deferred
after_status: corrected
decision_reason: CSVとPDFを確認し、最終値は11と判断
```

」

### フロー説明

「つまり、こういうフローが見えます：

```
P16（初期状態）
  ↓
review_required（『要確認』と判定）
  ↓
保留（『あとで確認する』）
  ↓
修正（『11に直す』）
  ↓
corrected（『修正済み』）
```

」

### まとめ

「重要なポイントは：

1. 『信頼度が低い』『値が不一致』という『危なそう』なものを先に見つける
2. 保留したり、段階的に対応できる
3. 対応の履歴と理由が全部残る

です。」

「誰が、いつ、何を、なぜ修正したか、完全に追跡可能です。」

## P30説明トーク（3分）

### セットアップ

「最後の例がP30です。」

「このケースは少し特殊で『AIとCSVが一致しても、人間が修正する』という例です。」

「画面を見ると、

```
v3値: 2
v22値: 1
CSV値: 1
confidence: high
classification: auto_confirm_candidate
```

」

### 重要なポイント

「v22とCSVが『1』で一致していて、confidenceも『high』で、『auto_confirm_candidate（自動確定候補）』と判定されています。」

「通常なら『確定しちゃっていいんじゃないか』と思うかもしれません。」

「でも、実はこのページ、人間がPDFを詳細確認したら『0』が正しかったんです。」

### 価値説明

「これが『確認支援ツール』の重要なポイントです。」

「AIとCSVが一致していても、人間の最終確認を優先できる。」

「これが『誤確定防止』です。」

### 操作

「では、『手動修正』で『0』に修正してみます。」

[→手動修正 選択]

「修正値：0」

「理由：『PDFを詳細確認したら0が正しい。手書きが薄い。』」

[→操作記録 ボタンをクリック]

「確認ログが記録されました：

```
user_action: correct
user_decision: manual_correct
manual_correction_value: 0
final_value: 0
before_status: auto_confirm_candidate
after_status: corrected
decision_reason: PDFを詳細確認したら0が正しい。手書きが薄い。
```

」

### CSV確認（重要）

「ここで重要な確認を1つ。」

「『確認ログをCSVでダウンロード』してみます。」

[→CSVダウンロード ボタンをクリック]

「このCSVを開くと、manual_correction_valueが『0』になっています。」

「『0.0』ではなく『0』です。これは数値として正しく保持されています。」

「『0が空欄扱いにされない』というのは意外と重要なポイントで、データの正確性を保証しています。」

### まとめ

「P30が示すポイント：

1. AIとCSVが一致していても、人間が見て『違う』と判定できる
2. 『AIが正しい』と盲目的に従わない
3. 修正理由が記録されるので、『なぜ0に修正したのか』が後から分かる

ここまで来ると、『これは確実に誤確定を防げるな』という手応えが出てくると思います。」
