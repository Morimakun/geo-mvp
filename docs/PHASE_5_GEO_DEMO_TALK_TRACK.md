## 📊 デモが説明する5つの軸

### 1. 最初に低く見えた原因
PDFページ番号とCSV行番号を単純に対応させていたため、別店舗・別日付のCSV行と比較していた。

### 2. 正しい照合キー
店舗名を取扱コード（列281）に変換し、帳票日付（列283）と組み合わせる。この店舗×日付キーで、Salesforceの正しい行を特定する。

### 3. 結果
評価対象14ページで13ページ一致、92.86%の高い整合を確認。

### 4. 残課題
再送FAX、店頭/イベント分離、CSV対象期間外、店舗未特定など、業務ルール確認待ち。

### 5. 提案価値
AI単体の精度ではなく、PDF帳票・Salesforce CSV・店舗マスターを組み合わせた確認支援システム。確認作業を効率化し、誤確定防止が最優先。

## P16説明トーク（5分）

### セットアップ

「次にP16の例です。こちらは『要確認』という判定です。」

「画面を見ると、

```
v3値: 9
v22値: 2
CSV値: 11
confidence: low
classification: review_required
```

という状態です。」

### 背景説明

「v3が『9』、v22が『2』、CSVが『11』と、すべて異なります。」

「しかも、V2.2の信頼度（confidence）が『low』になっています。」

「『confidence が low』というのは『このAI値は信じにくいかもしれない』ということです。」

### 対応方針

「こういう場合、自動確定ではなく『要確認』に分類します。」

「『要確認』は『ここは人間で見たほうがいい』というサインです。」

「では、このアイテムがどういう対応フローになるか見てみましょう。」

### 操作1：保留

「まず『保留』にしてみます。」

[→保留 ボタンをクリック]

「『保留』というのは『今すぐ判定しない。後で改めて確認する』ということです。」

「確認ログに以下が記録されました：

```
user_action: defer
user_decision: needs_follow_up
before_status: review_required
after_status: deferred
```

」

「『需要フォローアップが必要』『状態は保留』と記録されています。」

### 操作2：手動修正（後フェーズ）

「では、その後、確認が進んで『修正が必要』と判定した場合のフローです。」

「P16を再度選択します。」

「今度は『手動修正』を選択します。」

[→手動修正 選択]

「修正値を『11』に入力します。」

「理由は『CSVとPDFを確認し、最終値は11と判断』と入力します。」

[→操作記録 ボタンをクリック]

「新しいログが記録されました：

```
user_action: correct
user_decision: manual_correct
manual_correction_value: 11
final_value: 11
before_status: deferred
after_status: corrected
decision_reason: CSVとPDFを確認し、最終値は11と判断
```

」

### フロー説明

「つまり、こういうフローが見えます：

```
P16（初期状態）
  ↓
review_required（『要確認』と判定）
  ↓
保留（『あとで確認する』）
  ↓
修正（『11に直す』）
  ↓
corrected（『修正済み』）
```

」

### まとめ

「重要なポイントは：

1. 『信頼度が低い』『値が不一致』という『危なそう』なものを先に見つける
2. 保留したり、段階的に対応できる
3. 対応の履歴と理由が全部残る

です。」

「誰が、いつ、何を、なぜ修正したか、完全に追跡可能です。」

## P30説明トーク（3分）

### セットアップ

「最後の例がP30です。」

「このケースは『最も重要な警告例』で、『参考一致候補でも、人間確認を優先する』という事例です。」

「画面を見ると、

```
v3値: 2
v22値: 1
CSV値: 1
confidence: high
classification: auto_confirm_candidate（参考一致候補）
```

」

### ⚠️ 危険性の明示（最重要）

「v22とCSVが『1』で一致していて、confidenceも『high』です。」

「『自動確定候補だから、確定してもいいのでは？』と思うかもしれません。」

「しかし—PDF原票を人間が詳細確認したら『2』が正しいことが判明しました。」

「つまり、AIとCSVが一致していても、実際の原票と異なるケースがあるということです。」

### 本番初期の方針（最重要）

「そこで、本番初期では『参考一致候補』は参考情報として表示されますが、自動確定は行いません。」

「必ず人間が確認し、その履歴をログに残します。」

「これが『誤確定防止』の設計です。」

### 操作

「では、『手動修正』で『2』に修正してみます。」

[→手動修正 選択]

「修正値：2」

「理由：『PDFを詳細確認したら2が正しい。v3と一致。』」

[→操作記録 ボタンをクリック]

「確認ログが記録されました：

```
user_action: correct
user_decision: manual_correct
manual_correction_value: 2
final_value: 2
before_status: auto_confirm_candidate（参考一致候補）
after_status: corrected
decision_reason: PDFを詳細確認したら2が正しい。v3と一致。
```

」

### CSV確認（重要）

「ここで重要な確認を1つ。」

「『確認ログをCSVでダウンロード』してみます。」

[→CSVダウンロード ボタンをクリック]

「このCSVを開くと、manual_correction_valueが『2』になっています。」

「『2.0』ではなく『2』です。これは数値として正しく保持されています。」

「『0が空欄扱いにされない』『小数点が付かない』というのは意外と重要なポイントで、データの正確性を保証しています。」

### 本番での利用（最重要）

「P30が示すポイント：

1. 『参考一致候補』はあくまで参考情報
2. AIとCSVが一致していても、原票と異なるケースが存在
3. 本番初期は『すべてのページで人間確認』が必須
4. 修正理由が記録されるので、『なぜ2に修正したのか』が後から分かる
5. データを蓄積してから『低リスク候補の自動化』を段階的に検討

つまり、『100%自動化』ではなく『確認を効率化する支援ツール』として設計されています。」
