# 正の字カウント読み取りポリシー

## 概要

ジオソリューションズの日報FAX帳票では、数値欄にアラビア数字と正の字（tally marks）が混在して記入されます。本ドキュメントは、Vision API による自動抽出の精度向上と、誤判定リスク軽減のためのポリシーを定めます。

---

## 1. 帳票の手書き欄の現状

### 1.1 記入形式の多様性

日報帳票の数値欄には、以下の記入形式が存在します：

- **アラビア数字**: 1, 2, 3, ... 通常の数値表記
- **漢数字**: 一（ひとつ）、二、... 
- **正の字（tally marks）**: 完成形で5カウント

### 1.2 正の字の形態

正の字の完成形：「正」

途中形：
- 横線1本: 「一」のような形 → **1カウント**
- 横線+縦線: 「T」のような形 → **2カウント（疑い）**
- さらに線が増えた形 → **3カウント、4カウント（疑い）**

---

## 2. AI自動抽出の課題

### 2.1 読み取り可能なパターン

Vision API が**確実に認識できる**パターン：

1. **アラビア数字** (1, 2, 3, ...)
   - 精度: **高い** (90%以上)
   - リスク: **低い**

2. **完成した「正」**
   - 特徴: 5本の線が明確に見える
   - 精度: **中程度** (70%)
   - リスク: **低~中程度**

3. **明確な「一」（横線1本）**
   - 特徴: 単一の横線、罫線と区別可能
   - 精度: **高い** (80%)
   - リスク: **低い**

### 2.2 読み取り困難なパターン

Vision API が**不安定に判定する**パターン：

1. **T字形（横線+縦線）**
   - 特徴: 短い横線と縦線の組み合わせ
   - 見え方: 「正」の途中形か、ただの記号か区別困難
   - AI誤判定の傾向:
     - 「1」と判定（過小評価）
     - 「2」と判定（過剰評価）
     - 「null」を返す（保守的）
   - 精度: **低い** (40-50%)
   - リスク: **高い**

2. **罫線と重なった形**
   - 特徴: 帳票の縦線または横線と重なっている
   - 見え方: 正の字なのか罫線なのか不明瞭
   - AI誤判定の傾向:
     - 存在しない値を抽出する（false positive）
     - 実は記入された値を見落とす（false negative）
   - 精度: **非常に低い** (20-30%)
   - リスク: **非常に高い**

3. **書き癖による不規則な形**
   - 特徴: 個人の書き方で形が異なる
   - 見え方: 正の字の規則形から外れている
   - AI誤判定の傾向: ケースバイケースで判定ばらつき
   - 精度: **不安定** (30-60%)
   - リスク: **中~高い**

### 2.3 実装例：Vision API の実際の挙動

#### ケース1: 「一」形を「2」と誤判定

**Prompt**: 「T字形は2カウント、横線1本は1カウント」と強く指示
↓
**結果**: 
- 「一」形（実は1カウント）→ 「2」と返す（誤判定）
- 「T」形（実は判定困難）→ 「2」と返す
- **副作用**: 判定の区別が不可能に

#### ケース2: 「T」形を「null」と保守的に判定

**Prompt**: 「判定困難な形は null を優先」と指示
↓
**結果**:
- 「一」形（実は1カウント）→ 「1」と返す（正常）
- 「T」形（実は判定困難）→ 「null」と返す（保守的）
- **効果**: 実装可能なパターンは正しく認識、曖昧なものは要確認に

## 3. 初期版（MVP）の方針

### 3.1 自動確定するパターン

以下のパターン**のみ**を自動確定します：

| パターン | 判定基準 | 返却値 | 信頼度 |
|---------|---------|--------|--------|
| アラビア数字 | 明確に読める | そのまま | 高 |
| 完成「正」 | 5本線すべて確認 | 5 | 中 |
| 明確「一」 | 単独の横線、罫線と区別 | 1 | 高 |
| 完全空欄 | 何も記入なし | null | 高 |

### 3.2 要確認（needs_review / uncertain）に回すパターン

以下のパターン**は自動確定せず、人間確認対象に回します**：

| パターン | 判定基準 | 返却値 | 対応 |
|---------|---------|--------|------|
| T字形 | 横線+縦線の形 | uncertain / null | 人間が 1/2 のいずれか確認 |
| 途中形（3/4） | 3本以上4本以下の線 | uncertain / null | 人間が正確な画数を確認 |
| 罫線重複 | 帳票罫線と混在 | uncertain / null | 人間が実物を確認 |
| 不規則形 | 書き癖で形が異なる | uncertain / null | 人間が意図を確認 |

## 4. 実装上の考慮

### 4.1 期待値定義（Test Fixtures）

テストで期待値を設定する際の基準：

```
- expected = 1: 「一」形で確実
- expected = 2: 「正」の2カウント形で確実（稀）
- expected = 5: 「正」完成形で確実
- expected = "uncertain": 判定困難な形、または形状が曖昧
- expected = null: 空欄、または存在しない
```

### 4.2 評価ロジック

```python
if expected == "uncertain":
    # null でも数値でも acceptable
    # → 人間が確認対象として扱える状態
    result = "acceptable"
elif expected == 1:
    if actual == 1:
        result = "success"
    else:
        result = "failed"
```

### 4.3 Vision API Prompt の設計原則

1. **確実性優先**: 「可能性がある」ではなく「確実に見える」で判定
2. **null優先**: 判定困難なら数値化より null + 理由を優先
3. **副作用回避**: 特定パターン指示で他パターンへの誤影響を最小化
4. **曖昧性の明示**: 「この形は 1 または 2 の可能性」と書かない
   （代わりに: 「形が不明確な場合は null」と書く）

## 5. 段階的な本番化への道筋

### Phase 1: MVP（現在）

**自動確定**: アラビア数字、明確「一」、完全空欄  
**要確認**: T字形、途中形、罫線重複  
**評価**: Test fixtures で期待値を明示、Vision API の limit を理解

### Phase 2: 精度向上（検討中）

- 複数ページでの統計的検証
- より多くのサンプル収集
- 手書き「T」と「2」の区別基準の確立
- bounds / zoom の微調整

### Phase 3: 本番化（将来）

- 要確認項目の人間確認ワークフロー整備
- 確認結果のフィードバックループ
- 段階的な自動確定パターンの拡大
- ただし、完全自動化は目指さない（人間確認を常に含める）

## 7. 意思決定の根拠

### 7.1 なぜ「確実性優先」か

正の字の読み取りは、自動判定の信頼度が不十分（40-50%）です。  
完全自動化を目指さず、**確実な値のみ自動化、曖昧な値は人間判定** という方針が、長期的な運用効率を高めます。

### 7.2 なぜ「null優先」か

Vision API は「T字形は 1 である」と誤判定する可能性があります。  
「存在しない値を返す」より「判定困難と明示」する方が、後の修正が容易です。

### 7.3 なぜ「uncertain フラグ」か

「数値が null」と「判定困難」を区別することで、人間レビュー画面で対応を変えられます。

- null: スキップ（確認不要）
- uncertain: フラグ表示（確認対象）
