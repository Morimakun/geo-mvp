## 5. 片山様へ確認すべき事項が変わるか

### 明石大久保の扱い（確定）

以下を明記する：

1. **当初は「CSV側で追加入力された」可能性を想定していた**（帳票提出後にSalesforceへ後追いで実績を入力するケースを疑っていた）
2. **しかし高解像度クロップで確認した結果、PDF原本の合計欄は「2」と明確に読める**
3. **CSVも2であり、PDF原本とCSVは一致している可能性が高い**
4. **転記シートのみ0のため、確認するなら「転記シート側の反映漏れ・転記漏れ」観点になる**
5. **したがって、明石大久保はPDF×CSV照合の失敗例ではなく、むしろ転記シート差異検出の参考例として扱う。** 「帳票とCSVが一致しない」という当初の枠組みではなく、「帳票・CSVは一致しているのに、内部の転記シートだけがズレている」という別種の検出例である。

確認文案は、片山様に原因究明を丸投げする書き方より、「転記シートに漏れがあった可能性があるため、恐れ入りますが該当日の転記内容をご確認いただけますでしょうか」という**具体的な依頼**に調整済み（`PHASE_6_CLIENT_CONFIRMATION_ITEMS.md` セクションA参照）。

### くずはモール・大日の扱い（更新・2026-07-08）

本Vision試験の時点では新事実が得られず「変更不要」としていたが、**その後の目視再確認（`PHASE_6_MISMATCH_RECHECK_RESULT.md`）で両店とも新知見が得られた**：

- **くずはモール**：PDF原本＝転記シート＝7で一致。**CSVのみ13**（新規分だけ+6）。→ 明石大久保とは逆パターンで、**CSV側で新規分が追加入力されている可能性**
- **イオンモール大日**：旧帳票に合計欄が2箇所あり、上部（正の字タリー・確度中で4に近い）は転記シートに近く、下部（明確に6）はCSVと一致。→ どちらを紹介総数として扱うべきかという論点が新たに発生

確認文案はこの2店についても更新済み（`PHASE_6_CLIENT_CONFIRMATION_ITEMS.md` セクションA参照）。

### 変更不要：B（イベント計上ルール）
P8の帳票区分読み取りが割れた件は、**Vision抽出の技術的な弱点**であり、片山様への質問内容（イベント計上ルールの確認）自体には影響しない。当初のPAIRING文書での目視判定（P8=イベント）は高解像度クロップで裏付けられており、確認文案はそのままで問題ない。

### 新たな内部メモ（先方には送らない）
- ボックス選択項目（帳票区分・提出区分）は、印刷ラベルの数字との混同が起きるため、**本実装時はプロンプト設計に注意が必要**（今回は設計・変更しない）
- 数字の1〜2桁誤読（スタッフID・日付）が実際に発生する。**照合キーに帳票記載日付を使わない方針（画面選択日付を主キーとする）は、この誤読リスクを回避する観点でも妥当性が高い**ことが今回のテストで補強された
