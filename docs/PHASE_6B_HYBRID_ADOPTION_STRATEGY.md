# Phase 6B: case_items ハイブリッド採用戦略

**作成日**: 2026-06-07  
**目的**: 全部 v5 / 全部 v3 ではなく、項目別に最適方式を選択  
**戦略**: 項目ごとに v3 / v5 / v5.2 を使い分けるハイブリッドアプローチ

---

## 📋 前提

```
全体判定: v5 は採用候補ではない（実装品質不足）
ただし AZ は改善している（14% → 71%）
ただし AV は危険誤読削減している（3 zeros → 0）

→ 項目別の個別判定が必要
→ 全部置き換えではなく、ハイブリッド実装を検討
```

## 🎯 項目別推奨方式

### AU（au案件新規）

| 指標 | v3 | v5 |
|------|-----|-----|
| 成功率 | 4/7 (57%) | 2/7 (29%) |
| zeros | 2/7 | 1/7 |

**推奨**: **v3 MAINTAIN** ✅

**理由**:
```
- v5 は成功率も下がり、zeros 削減のメリットが小さい
- v3 の 57% は許容できるベースライン
- リスク/メリット比が v5 採用に値しない
```

---

### AV（au案件既存）

| 指標 | v3 | v5 |
|------|-----|-----|
| 成功率 | 3/7 (43%) | 0/7 (0%) |
| zeros | 3/7 (危険!) | 0/7 (全削除) |

**推奨**: **v5.2 に優先対応** 🔴

**理由**:
```
【問題】
  v3 の 43% が zeros = 異常に高い危険誤読
  → 案件欄では 0 はあり得ない（空欄誤読の可能性大）

【v5 の評価】
  v5 は zeros を完全削除（危険大幅軽減！）
  ただし値も全て null になった（実装失敗）
  → crop bounds が不適切

【対応】
  v5.2 で bounds を調整
  → 値を返しながら zeros を削除できるか検証
  → 成功すれば高い価値がある

【フォールバック】
  v5.2 が失敗した場合は v3 継続
  ただし「危険な誤読」として記録
```

**判定基準（v5.2 採用）**:
```
✅ v5.2 が v3 以上の成功率を達成
✅ zeros が 3 → 1 以下に削減
✅ nulls が excessive でない（<80%）
```

### AY（その他案件新規）

| 指標 | v3 | v5 |
|------|-----|-----|
| 成功率 | 2/7 (29%) | 1/7 (14%) |
| zeros | 0/7 | 0/7 |

**推奨**: **v3 MAINTAIN** ✅

**理由**:
```
- v3 ベースラインが既に低い (29%)
- v5 はさらに悪化（14%）
- 危険誤読がないため、改善のインセンティブも低い
- 低優先度（v5.2 の対象外）
```

### AZ（その他案件既存）

| 指標 | v3 | v5 |
|------|-----|-----|
| 成功率 | 1/7 (14%) | 5/7 (71%) |
| zeros | 0/7 | 2/7 (新規発生!) |

**推奨**: **v5 条件付き採用** ⚠️

**理由**:
```
【成功率の大幅改善】
  14% → 71% は劇的な改善
  → 分割 crop の有効性を証明

【新しいリスク】
  v5 で新しく 2 個の zeros が出現
  → 空欄を 0 と誤読している可能性

【判定】
  メリット（データ量 5 倍化）vs デメリット（new zeros 2 個）
  → 運用上許容できるか確認が必要
```

**判定基準（v5 採用）**:
```
✅ メリット（71% 成功率）が 2 個の new zeros を正当化するか
✅ CSV マッチング時に new zeros が誤った結果を招かないか
✅ 運用チームが「more data with acceptable risk」を認可するか
```

**判定基準（v5 不採用）**:
```
❌ new zeros は許容できない
→ v3 継続（14% ベースライン）
```

### AI（案件合計：数字欄）

| 指標 | v3 | v5 |
|------|-----|-----|
| 成功率 | 7/7 (100%) | 0/7 (0%) |
| 評価 | 完璧 | 完全失敗 |

**推奨**: **v3 MANDATORY（v5.2 待機）** 🔴🔴

**理由**:
```
【致命的な問題】
  v3 は 100% 成功（完璧なパフォーマンス）
  v5 は 0% 成功（全て null）
  
【根本原因】
  AI 行の crop bounds 高さが 0.5% で小さすぎる
  → Vision API が画像として認識不可

【対応】
  v5.2 で AI crop bounds を拡張
  高さ: 0.5% → 1.5-2.0% に調整
  目標: v3 の 100% を回復

【重要性】
  AI は「合計」欄 = CSV 照合で重要な項目
  絶対に null を増やしてはいけない
```

**判定基準（v5.2 採用）**:
```
✅ v5.2 で AI が 80% 以上の成功率を回復
✅ v3 の 100% には及ばなくても、許容可能な範囲内
```

**判定基準（v5.2 不採用）**:
```
❌ v5.2 でも回復しない場合
→ v3 継続（100% 成功を維持）
```

## 🔄 ハイブリッド実装戦略

### 全体構成

```
case_items 抽出処理:

Tier 1 (v3 維持):
  ✅ AU  → v3 (no change needed)
  ✅ AY  → v3 (no change needed)
  ✅ AI  → v3 (until v5.2 fix)

Tier 2 (v5 条件付き):
  ⚠️  AZ  → v5 (if trade-off approved: 71% success vs 2 new zeros)

Tier 3 (v5.2 待機):
  🔴 AV  → v5.2 (HIGH priority: danger reduction opportunity)
  🔴 AI  → v5.2 (CRITICAL: recovery to 80%+ target)
```

### 実装方針

```python
# 擬似コード: case_items_hybrid()

def extract_case_items_hybrid(pdf, page_index):
    """
    Hybrid extraction: v3, v5, v5.2 の組み合わせ
    """
    
    results = {}
    
    # AU: v3 method
    results['AU'] = extract_au_v3(pdf, page_index)
    
    # AV: v5.2 method (or v3 fallback)
    if v52_available and av_danger_approved:
        results['AV'] = extract_av_v52(pdf, page_index)
    else:
        results['AV'] = extract_av_v3(pdf, page_index)
    
    # AY: v3 method
    results['AY'] = extract_ay_v3(pdf, page_index)
    
    # AZ: v5 method (if trade-off approved)
    if az_new_zeros_acceptable:
        results['AZ'] = extract_az_v5(pdf, page_index)
    else:
        results['AZ'] = extract_az_v3(pdf, page_index)
    
    # AI: v3 method (or v5.2 if recovered)
    if v52_ai_recovered_to_80_plus:
        results['AI'] = extract_ai_v52(pdf, page_index)
    else:
        results['AI'] = extract_ai_v3(pdf, page_index)  # Mandatory
    
    return results
```

### 利点

```
✓ 項目ごとのカスタマイズ
  → AU/AY のような低改善項目は v3 維持
  → AV/AI のような高優先度項目は v5.2 待機
  → AZ のような改善項目は条件付き v5

✓ リスク最小化
  → AI は完璧な v3 を維持
  → 新しい zeros は許容範囲内
  → 失敗時のフォールバックが明確

✓ 段階的改善
  → v5.2 が実装されたら項目単位で切り替え可能
  → 将来の v5.3 / v6 にも拡張可能
  → 本格導入まで全て v3 で実行可能

✓ 証拠ベースの決定
  → 各項目の改善効果を定量的に評価
  → トレードオフを明示的に記録
  → 運用チームの意思決定を支援
```

## 📌 重要な注記

### AV の危険誤読について

```
現在の v3:
  AV の 43% が zeros = 異常値
  理由: crop bounds が不適切 + 正の字誤読
  
このままでは:
  CSV マッチング時に「実績 0 件」と見做される
  実際には「空欄」なのに「0 件」として処理
  
v5.2 の意義:
  zeros を減らせば、データの信頼性向上
  → 運用チームから期待が大きい
```

### AZ の新しい zeros について

```
改善 (14% → 71%) vs リスク (0 zeros → 2 zeros)

二者択一ではない:
  - 新しい 2 個の zeros が「危険」なのか「許容可能」なのか
  - 運用業務の観点から判断が必要
  - 提案: 運用チームに「71% success + 2 zeros」を明示して相談
```

### AI は絶対に動かすな

```
v3 の 100% 成功率は珍しい
  → 他のフィールドと比べても断トツの信頼性
  → CSV 照合で「合計」は重要フィールド
  → null 化は致命的なリグレッション

v5.2 で必ず回復させる前提
  → 回復できなければ v3 維持
  → 80% まで回復できれば検討可
```
