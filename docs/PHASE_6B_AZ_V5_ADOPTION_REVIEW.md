## 🎯 採用可否の判定

### **判定結果: D. 条件付き不採用（後処理あれば条件付き採用）**

#### パターンA: 後処理なし → **不採用**

```
理由:
  ❌ P08/P15 の新しい0が危険
  ❌ 後処理ロジックなし
  ❌ CSV照合時に「0件」と誤認識される可能性
  ❌ 運用リスク > 改善メリット
  
結論: v3 継続（14%ベースライン）
```

#### パターンB: 後処理あり → **条件付き採用**

```
後処理ロジック:
  IF v5_AZ == 0:
    → uncertain に変換（自動確定しない）
    → review_reason に「zero_in_tally_field」を付与
    → 手動確認待ち

メリット:
  ✓ P01/P06/P10 の改善は活かせる
  ✓ P08/P15 のリスク0を自動確定しない
  ✓ 操作者が手動で検証可能

リスク:
  - P08/P15 のレビューが手動業務負担
  - ただし「危険な自動確定」より安全

条件:
  ✅ 運用チームが「レビュー負担」を了承
  ✅ 後処理ロジックを実装（app.py等）
  ✅ CSV出力時に「uncertain」フラグを表示
```

## 💾 後処理案の詳細

### 案A: v5 AZ=0 を全て null に変換（最安全）

```python
# ハイブリッド実装時
def extract_case_items_hybrid(pdf, page_index):
    results = {}
    
    # ... 他の項目 ...
    
    # AZ: v5採用（後処理あり）
    az_value = extract_az_v5(pdf, page_index)
    
    # 後処理: v5でAZ=0の場合は null に変換
    if az_value == 0:
        results['AZ'] = None  # 零を信頼しない
        results['AZ_reason'] = 'zero_in_tally_field'  # 理由記録
    else:
        results['AZ'] = az_value
    
    return results
```

**効果**: 
- P08/P15 の0は確定されない
- P01/P06/P10 の改善は活かされる
- 運用チームが手動検証

**デメリット**: レビュー業務負荷

### 案B: v5 AZ=0 を「uncertain」フラグ付きで保持（柔軟性重視）

```python
def extract_case_items_hybrid(pdf, page_index):
    results = {}
    
    # ... 他の項目 ...
    
    # AZ: v5採用（後処理あり）
    az_value = extract_az_v5(pdf, page_index)

    if az_value == 0:
```

**効果**:

- 運用チームが「このレコード確認が必要」と判定可能

**デメリット**: 「0」が使われる可能性（リスク）

## 📌 重要な注記

### AZ=0 が危険な理由

```
AZは「その他案件既存」= 既存顧客への追加提案
  - 通常は「空欄」（提案なし）か「正の字」（提案あり）
  - 0（ゼロ）は意味がない
  - 正の字1本を「0」と誤読すると、実績喪失

CSV照合時の影響:
  「既存案件 0件」と見做される
  → 実績データ不整合
  → Salesforce集計が狂う

視認結果:
  - P008: 空欄が「0」と読まれた
  - P015: 「1」が「0」に変わった（最悪ケース）
```
