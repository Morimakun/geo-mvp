# Phase 5 - ジオソリューションズ向け ゴールデンデータセット（正解データセット）仕様書

**作成日:** 2026-06-08  
**対象:** 本格導入判断に向けた精度検証基盤構築  
**主眼:** 以後の改善施策の効果を測定するための「正解データ」を整備する

---

## 目的：なぜ正解データセットが必要か

### 現状の課題

```
現在、精度を「推定値」で語っています：
  ├─ 自動確定候補の正解率：「約 85～90%」（30ページ肌感）
  ├─ 危険誤確定率：「不明」（想定値）
  ├─ 要確認捕捉率：「約 80～85%」（検証不十分）
  └─→ これらは「実装後の推測」であって、測定値ではない

その結果：
  ① 「精度が上がったか」を客観的に判定できない
  ② スコアリングの基準が信頼されない
  ③ 本格導入判断の根拠が弱い
```

### 正解データセットとは

```
「業務を理解した専門家が、PDF と Salesforce CSV を確認して
 確定した値」を 100ページ（以上）保有する

例：
  page=14, store_code=001, field_code=AI合計欄
  AI値=3, CSV値=3, final_judgment=3 (確定)

この「final_judgment」が「正解」です。
```

### 正解データセットの用途

```
以後のすべての改善施策を、これに対して検証します：

① 異常値チェック導入
   └─ 「導入前 vs 導入後」で誤確定件数が減ったか、測定可能

② スコアリング改善
   └─ スコア導入後の「自動確定正解率」「要確認捕捉率」を正確に算出

③ マスタ整備
   └─ マスタ整備後の「CSV候補特定率」が向上したか測定

④ Confidence校正
   └─ Confidence HIGH/MEDIUM/LOW の正解率を測定し、加点調整

⑤ 帳票改善
   └─ 帳票改善後の誤読減少度を測定

つまり、「Before / After」で改善効果を定量的に示せます。
```

## 対象ページ数と抽出方針

### 最低 30ページ、推奨 100ページ以上

```
30ページ：最小限のデータセット
  └─ 主要エラーパターンを把握するのに必要

100ページ：本格的な効果測定に必要
  └─ 店舗別・FAX品質別・日付別などの層別分析が可能
  └─ 統計的信頼性が上がる（n=100 で各層 n≧5 程度確保可能）

200ページ以上：さらに詳細な分析が可能
  └─ 本格導入後の追加改善に備える
```

### サンプル抽出方針（100ページの場合）

```
母集団：ジオ様から提供いただく「直近3ヶ月分のすべてのページ」

サンプリング戦略：
  ├─ 層別ランダムサンプリング（店舗別、FAX品質別、日付別）
  ├─ 店舗別：10店舗 × 10ページ = 100ページ
  ├─ FAX品質別：高品質 40 / 中品質 40 / 低品質 20
  ├─ 日付別：月の前半（30ページ）/ 中盤（35ページ）/ 後半（35ページ）
  └─ 手書き濃淡別：濃い（40ページ）/ 通常（40ページ）/ 薄い（20ページ）

効果：
  → 母集団全体の特性をバランスよく代表する
  → 店舗別・FAX品質別の層別分析が可能
  → 「この品質レベルではどう」という具体的改善提案ができる
```

## 正解データセットに含める項目

### スキーマ案

```csv
golden_dataset_id,page,business_date,store_name,store_code,staff_name,tablet_no,
ai_total_value,csv_total_value,final_judgment,
ai_confidence,v3_value,
target_cell_found,image_quality,handwriting_density,
error_type,csv_candidate_count,
confirmed_by,confirmed_at,notes
```

### 各項目の説明

| 項目 | 説明 | 例 |
|------|------|-----|
| **golden_dataset_id** | 正解データセットの一意ID | GD_20260613_P14 |
| **page** | ページ番号 | 14 |
| **business_date** | 業務日付（PDF記入日） | 2026-06-01 |
| **store_name** | 店舗名 | 青山店 |
| **store_code** | 店舗コード | 001 |
| **staff_name** | 担当者（手書き） | 山田太郎 |
| **tablet_no** | タブレット番号（記入デバイス） | TAB-001 |
| **ai_total_value** | AI が読み取った合計値（V2.2） | 3 |
| **csv_total_value** | Salesforce CSV の値 | 3 |
| **final_judgment** | 確定値（正解） | 3 |
| **ai_confidence** | AI の confidence レベル | HIGH / MEDIUM / LOW |

## 正解データセット作成フロー

### 一次確認（業務担当者 1 名）

```
① PDF を確認
  └─ AI値、v3値を視認し、「正しい値はどれか」を判定

② Salesforce CSV を確認
  └─ CSV側の値、マスタ情報を確認

③ final_judgment を記入
  └─ 「この項目の正解は『3』」と確定
  └─ その根拠を notes に記載（例：「PDFを詳細確認し、3 が正しい」）

④ error_type を分類
  └─ AI値と最終値が異なるなら、誤りの種類を記入
  └─ 例：「34→3（桁誤読）」→ error_type = "桁誤読"
```

### 二次確認（別の業務担当者または上司）

```
① 一次確認結果を確認
  └─ final_judgment に異議がないか確認

② 不一致の場合は協議
  └─ 「AI=2, CSV=11, 一次確認者=11」で不一致の場合
  └─ 二次確認者が「本当に 11 が正しいのか」を再検証

③ 最終合意
  └─ 二次確認者も同意したら、final_judgment を確定
  └─ 不一致が続く場合は上級者・経営判断を仰ぐ
```

### ゴールデンデータセット登録

```
Step 1: 一次・二次確認完了した 100 ページを集約
Step 2: final_judgment, error_type, confirmed_by, confirmed_at を記入
Step 3: CSV形式で保存（UTF-8 with BOM）
Step 4: 以後のすべての改善検証で参照
```

## 正解データセットの評価指標

### Phase B（100ページ検証）で測定する指標

```
① PDF抽出一致率
   定義：AI が正しくセルを認識した率
   式：(target_cell_found=TRUE の件数) / 全件数
   現状値：未確定（30ページベース推定 90-95%）
   評価基準案：実データ検証で設定

② CSV候補特定率
   定義：store_code 一致で正しい CSV 行を特定できた率
   式：(csv_candidate_count=1 かつ final_judgment=csv_value の件数) / 全件数
   現状値：未確定（推定 90-95%）
   評価基準案：実データ検証で設定

③ 自動確定候補の正解率
   定義：auto_confirm_candidate 分類されたうち、final_judgment と一致した率
   式：(auto_confirm AND ai_value=final_judgment の件数) / auto_confirm の全件数
   現状値：未確定（推定 85-90%）
   評価基準案：実データ検証で設定
   用途：スコアリング導入後の確認削減率予測に使用

④ 要確認捕捉率
   定義：実際に誤りだったもの（ai_value ≠ final_judgment）のうち、
       review_required に分類できた率
   式：(review_required AND error_type≠無し の件数) / 
        (error_type≠無し の全件数)
   現状値：未確定（推定 80-85%）
   評価基準案：実データ検証で設定
   用途：「危険なものを確実に拾えているか」の検証

⑤ 危険誤確定率
   定義：auto_confirm_candidate に分類されたが、実は誤りだった率
   式：(auto_confirm AND ai_value≠final_judgment の件数) / 
        auto_confirm の全件数
   現状値：未確定（推定 0.5-1%）
   評価基準案：業務影響が大きい項目は 0% を目指す
   用途：本格導入判断の重要指標

⑥ 確認削減率
   定義：自動確定候補により、確認が不要になった率
   式：(auto_confirm_candidate の件数) / 全件数 × 100%
   現状値：未確定（推定 60-70%）
   評価基準案：誤確定防止とのバランスで決定
   用途：「本当に 60% 削減できるか」の実測

⑦ 確認時間削減率
   定義：一件あたりの確認時間の短縮率
   測定方法：ジオ様の確認作業を実測（ストップウォッチ または UI ログ）
   式：(改善前の平均時間 - 改善後の平均時間) / 改善前の平均時間 × 100%
   現状値：未確定
   評価基準案：実運用で測定
   用途：ROI測定に使用
```

### エラー分類別集計

```
正解データセット 100 ページを error_type で仕分けして集計：

誤りの種類                  件数    比率    改善方向
────────────────────────────────────────────────────
① 桁誤読                   10件    50%     異常値チェック / Few-shot
② 手書き不鮮明             8件     40%     帳票改善 / 画像前処理
③ 正の字誤読               5件     25%     チェックボックス化
④ 対象セル誤認             3件     15%     セルクロップ改善
⑤ PDF画質不良             2件     10%     FAX品質チェック
⑥ CSV候補違い             4件     20%     マスタ整備
⑦ マスタ不足              2件     10%     マスタ拡充
⑧ CSV側入力ミス           3件     15%     CSV側フロー
⑨ 人間確認ミス            1件      5%     確認UX改善
⑩ 仕様未定義              1件      5%     業務ルール確認

※ 件数は例示。実データで集計する
```

結果から見える優先度：
```
「②手書き不鮮明が 40% → 帳票改善が投資先として最優先」
「①桁誤読が 50% → 異常値チェック実装が効く」
など、具体的改善ターゲットが見える化される
```

### 層別分析

```
① 店舗別エラー率
   └─「A 店舗の誤確定率が特に高い」が見える
   └─ 原因：タブレット機種？担当者スキル？FAX品質？

② FAX品質別エラー率
   ├─ 高品質FAX → エラー率 5%
   ├─ 中品質FAX → エラー率 12%
   └─ 低品質FAX → エラー率 25%
   └─「低品質 FAX に対しては事前に要確認に回すべき」という判定が可能

③ 担当者別エラー率
   └─「X 担当者の誤り率が高い」が見える
   └─ 原因：入力ミス？記入品質？
   └─ 改善対象（個人指導 or 帳票改善）が判明
```

## ジオ様にご提供いただきたい情報

### 実データ

```
□ PDF ファイル（100ページ分）
  ├─ 対象：直近 2～3 ヶ月分の全ページ
  ├─ 形式：PDFファイル（可能なら元々のスキャン品質を保持）
  └─ 命名例：GEO_2026_04_001.pdf, GEO_2026_04_002.pdf, ...

□ 対応する Salesforce CSV
  ├─ 対象：上記 PDF に対応した売上実績データ
  ├─ 含むべき列：store_code, business_date, item_a, item_b, ..., total
  └─ 行数：100 行（1ページ = 1 行）
```

### マスタ・参考資料

```
□ 店舗コード一覧
  ├─ 店舗名 → store_code のマッピング
  ├─ 店舗ごとの FAX 送信元情報
  └─ 店舗別の売上目安（エラー検出の参考に）

□ 担当者マスタ
  ├─ 名前表記の統一（手書き表記の揺れ対応）
  └─ 担当者 ID

□ タブレット番号一覧
  ├─ タブレット番号 → 店舗のマッピング
  └─ タブレット機種・FAX 機種情報

□ PDF 項目と CSV 列の対応表
  ├─ 「PDF の『合計欄』」= 「CSV の『total 列』」という対応
  ├─ 「PDF の『商品 A』」= 「CSV の『item_a 列』」という対応
  └─ これがあると AI の対象セル特定が正確になる

□ 確認担当者の名簿
  ├─ 一次確認者（何人？）
  └─ 二次確認者（何人？）
  └─ スケジュール（何日で完了させるか）

□ 業務ルール・正解判定基準
  ├─「CSV と PDF が異なる場合、どちらを正とするか」
  ├─「手書きが読めない場合の判定ルール」
  ├─「誤差の許容範囲はあるか」（例：±1 までは許容）
  └─ 「何が『許容できない誤り』か」（給与・評価に直結？）

□ 過去の確認ログがあれば提供
  └─「このページは過去に確認済みで、最終値は○」というデータ
```

## スケジュール目安

```
正解データセット構築全体：1～2 ヶ月

Week 1:   準備・サンプル抽出
          ├─ PDFと CSV の提供
          ├─ マスタ情報の確認
          └─ 一次・二次確認者の確認

Week 2-3: 一次確認
          └─ 一次確認者が 100 ページを確認（1 ページ 3～5 分目安）

Week 4:   二次確認・協議
          └─ 二次確認者が抜き取り or 全件確認
          └─ 不一致があれば協議

Week 5:   ゴールデンデータセット完成
          └─ final_judgment 確定
          └─ error_type 分類完了
          └─ CSV 形式で整備

Week 6+:  効果測定・改善計画策定
          └─ エラー分類集計
          └─ 優先度の高い改善施策を提案
```

---

## 注記

```
この正解データセットは：
  ✅ 以後のすべての改善施策の「検証基盤」です
  ✅ 「本当に効いたのか」を測定できます
  ❌ 「完全な正解」を保証するものではありません
  ❌ 業務的な誤りまでは検出できません（例：実際には在庫ミスで値が違う）

但し、AI が「読み取り誤り」をしたのか、
「業務ミス」なのかを区別できるようになります。
```
