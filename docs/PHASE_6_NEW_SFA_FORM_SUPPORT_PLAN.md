## 4. 照合キー方針

### 基本照合キー
```
(store_code, screen_selected_business_date, activity_type)
```

つまり：
- **店舗コード** ← 帳票上部の店舗コード（CSV col281 と対応）
- **画面で選択された帳票対象営業日** ← ユーザーが画面で選択した営業日
- **帳票区分** ← 店舗/イベント

### 帳票上の日付の扱い
- **抽出対象：** はい（取得する）
- **照合キー：** いいえ（参考値として扱う）
- **表示方法：** 確認画面に参考値として表示
- **ズレ判定：** 画面選択日とズレている場合は要確認フラグを立てる
- **理由：** FAX送信日と帳票対象営業日がズレることがあり、画面選択が正とする設計

### 店舗コードの前処理
```
1. 空白除去（前後の空白を削除）
2. 全角・半角の正規化
3. 文字列として保持
4. CSV col281 と比較

例：「ＡＵ１ＫＢ８３０２２７」→ 「AU1KB830227」
```

### スタッフ識別の優先順位
1. **スタッフID** ← 新帳票で追加、最も安定
2. **スタッフ名** ← 既存の name 相当、表記ゆれの可能性あり

スタッフ名は表記ゆれが起きやすいため、照合・確認時はスタッフIDをより重視します。

### 提出区分の役割
- **照合キーには使わない**
- **同一キーで複数帳票が届いた場合の確認フラグとして使う**

## 5. 実装の最重要原則：「チェックボックスはヒント、値比較が真実」

### 原則定義
```
チェックボックス・番号区分は「運用者の意図を示すヒント」であり、
実際の真実は「PDF帳票と Salesforce CSV の主要数値の一致・不一致」である。
```

これは以下を意味します：

- ✅ **値が同じ → 一致**（チェックボックスに関わらず）
- ✅ **値が違う → 不一致**（チェックボックスに関わらず確認対象）
- ✅ **チェック矛盾 → 確認フラグ**（値と矛盾する場合、要確認として浮かび上がらせる）
- ❌ **チェックボックス最優先ではない**（「再送（変更なし）」でも値が違えば確認対象）

### 判定ロジック（優先度順）
```
1. 値比較：主要数値（AI合計欄、CZ合計欄等）が同じか違うか
2. チェック矛盾判定：提出区分と値の差異が矛盾していないか
3. 確認フラグ：チェック矛盾があれば「要確認」「警告」レベルを決定
4. 優先候補：後から届いた帳票を優先候補にする（値比較の上で）
5. 自動採用：絶対にしない（最終判定は確認者）
```

## 6. 同一キーで複数帳票がある場合の処理フロー

### Case 1: `submission_type = resend_without_changes` なのに主要数値が異なる
```
判定：要確認
理由：再送（変更なし）なのに数値差異あり
可能性：OCR誤読 / 記入差異 / 黙示的な修正
表示：差異を赤色フラグで表示、確認対象に含める
```

### Case 2: `submission_type = resend_with_changes` で主要数値が異なる
```
判定：後送分を優先候補
理由：修正・差替宣言されている
表示：旧版との差分を明示、確認対象として表示
自動確定：しない（確認者が最終判定）
```

### Case 3: `submission_type = resend_with_changes` なのに主要数値が同じ
```
判定：軽微（確認優先度低）
理由：修正ありだが値変わらず
表示：情報の参考値として表示（低優先）
```

### Case 4: 提出区分が未読取・未記入で同一キーの2枚目がある
```
判定：要確認
理由：再送か修正か判断できない
表示：確認対象として表示、スタッフに問い合わせ対象
```

## 10. 実装前に確認する優先事項

### 10-1. 店舗活動無し（新帳票の新項目）

**背景：** 新帳票に「□ 店舗活動無し」欄が追加されている。

**扱い方：**

```
抽出項目：
- store_activity_none_raw（チェック有無の生値）
- store_activity_none_flag（真偽値に変換）

照合時のロジック：
1. store_activity_none_flag = True（チェック済み）
   → 主要合計欄がゼロ・空欄でも不一致にしない
   → 「活動なし報告」として扱う
   → CSV側もゼロ相当なら一致候補
   → CSV側に数値があれば要確認

2. store_activity_none_flag = False（未チェック）
   → 従来どおり主要合計欄とCSV値を比較

3. store_activity_none_flag = unknown（読み取り不可）
   → 値比較を優先し、必要に応じて要確認に回す
```

### 10-2. 帳票バージョン識別（旧/新混在対応）

**背景：** 切替後も旧帳票が届く可能性があり、両対応が必須。

**抽出項目：**

```
- form_version: 帳票様式の版（old_sfa / new_sfa_20260621 / unknown）
```

**版判定ルール（暫定）：**

```
新帳票判定：
- 帳票に「2026/6/21更新」表記あり
  OR
- 上部に「帳票区分（1 店舗 / 2 イベント）」「提出区分（1 初回 / 2 再送 / 3 再送）」がある

旧帳票判定：
- 従来項目のみ
- 帳票区分・提出区分が無い

判定不能：
- form_version = unknown → 要確認に回す
```

**旧帳票互換性：**

```
- 新帳票対応により、旧帳票の既存抽出・照合を壊さないこと
- form_version = old_sfa の場合は既存ロジックを適用
- form_version = new_sfa_20260621 の場合のみ新ロジックを適用
- どちらでもない（unknown）場合は、保守的に既存ロジックで試す
```

## 11. 合計欄位置の確認（静的・コード変更なし）

**目的：** AI合計欄（CSV列35「紹介総数」）・CZ合計欄（CSV列104「お声がけ総数」）が新帳票でも物理位置が大きく変わっていないか確認。

**実施内容：** 新帳票PDFのテキストレイヤから合計欄キーワード、座標を抽出・比較。

### 11-1. 新帳票での合計欄位置（静的確認結果）

**新帳票レイアウト（A4相当：595.32 × 841.92）：**

| 合計欄 | テキスト | 絶対位置 | 相対位置（比率） |
|--------|---------|---------|------------------|
| メイン | 「合計（数字で記入）」 | x=86~140, y=206~212 | left=0.14, top=0.24, right=0.23, bottom=0.25 |
| サブ | 「ポイント合計/項目合計（1～32）」 | x=422~490, y=628~632 | left=0.71, top=0.75, right=0.82, bottom=0.75 |

### 11-2. 既存コード（旧帳票想定）での合計欄位置

| 合計欄 | 相対位置（比率座標） | 用途 |
|--------|-------------------|------|
| left_totals | left=0.0, top=0.72, right=0.50, bottom=0.82 | 左下の合計欄 |
| right_totals | left=0.65, top=0.43, right=0.98, bottom=0.56 | 右下の合計欄 |

### 11-3. 位置比較と判定

⚠️ **重要：** 新帳票と旧帳票で**レイアウトが大きく異なる可能性**があります。

**理由：**
- テキストレイヤは「合計」キーワードを検出可能
- しかし、実際の数値入力欄（罫線・マス）の物理位置が旧帳票と異なる
- 新帳票の相対位置がテキストレイヤの「合計」タイトルを示しており、実データ入力欄はさらに下か横にある可能性

**精度判定のタイミング：**
- 空帳票の静的確認では位置の大まかな判定のみ可能
- **実記入・FAX送付された新帳票を受領後、実際にVision APIで抽出できるか検証が必須**
- 抽出失敗 or 精度低下の場合は、プロンプト・座標の調整が必要

**既存92.86%の前提：**
- 新帳票での合計欄抽出精度が著しく低下すれば、92.86%を新様式で再確認する必要がある

| **店舗名** | 中央配置 | **プレプリント**（より明確に配置） |

### 12.2. 番号体系の差分

**旧帳票：** セクションごとに番号体系が分かれている
- 案件関連：1〜4
- 内訳（mo光等）：①〜㉔
- その他：1〜35
- 新規オプション：実績ごと

**新帳票：** 1〜104 の通し番号に統一
- 通し番号が抽出時のアンカーとして活用できる可能性がある
- ただし、新SFA上の項目番号とCSV列番号の対応は**未確認**
- 新SFA運用後のCSVスキーマ確認時に、項目番号とCSV列の照合表をジオから受け取ることを想定

### 12.3. 新設・拡張された項目

**新設：**
- 通し番号80〜85：獲得年代別（20代、30代、40代、50代、60代、70代〜）
- 通し番号91：UQスポット件数
- 通し番号95〜101：稼働人員数、集客数、商談数、NET獲得数、TV獲得数、高速回付帯、**生産性（NET獲得数÷稼働人員数）**
- 通し番号102：**□ 店舗活動無し**（ただし配置がイベント実績ブロック末尾）

**拡張：**
- イベント実績欄が3項目から11項目に拡張（通し番号は旧と異なる）

**特に重要な新項目：**
- **店舗活動無し**：ゼロ報告・活動なし報告の判定に関わり、Phase 6の「store_activity_none_flag」で扱う予定

### 12.4. 削除・縮小された項目

- 旧帳票の「【事務局への連絡】自由記述欄」は新帳票では見当たらない
- 自由記述形式が廃止され、構造化された区分・番号・数値欄に寄せる方向
- これは初期版の「備考欄を入れない」方針と整合する

### 12.5. 合計欄・主要照合項目への影響

以下の定義は維持する：

```
AI合計欄 = CSV列35「紹介総数」
CZ合計欄 = CSV列104「お声がけ総数」
```

ただし、新帳票では物理レイアウトや番号体系が旧帳票と異なるため、旧帳票での検証結果（92.86%）をそのまま新帳票へ適用しません。

新帳票で実際に記入・送付されたPDFを受領後、以下を再検証します：

- [ ] AI合計欄の読み取り可否
- [ ] CZ合計欄の読み取り可否
- [ ] 店舗活動無しチェック時のゼロ/空欄扱い
- [ ] 同日Salesforce CSVとの一致状況

### 12.6. 実装への含意

**今の段階で分かったこと：**
- 新帳票対応では、旧帳票と新帳票の両対応が必須（`form_version` 分岐）
- 新帳票の通し番号1〜104は、抽出プロンプト上のアンカーとして活用できる**可能性がある**
- 店舗コードがプレプリント化されたことで、手書き読み取り精度の懸念が**部分的に緩和**される（ただしマス連動の手書き部分はまだ）

**実装前の確認事項：**
- 空帳票だけでは本抽出プロンプトを確定できない
- 記入済み新帳票＋同日Salesforce CSV受領後に、最小実装範囲を再確定する
- 特に「通し番号とCSV列の対応表」があるかどうかで、プロンプト設計が変わる可能性
