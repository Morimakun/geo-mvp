# 担当者名・所属店舗の正データ突き合わせ設計書

**Version**: 1.0  
**作成日**: 2026-05-29  
**対象**: FAX帳票 × Salesforce CSV 照合支援システム

---

## 📋 概要

PDF帳票のOCR読取では、担当者名の誤読・部分読取が発生することが確認されました（完全成功率70%）。

本設計書は、**OCR結果を正データマスタと突き合わせ、候補補正する方式**を提案します。

---

## 🔍 なぜ正データ突き合わせが必要か

### OCR単体の限界

**今回のサンプル（30ページ）テスト結果:**

| 項目 | テスト結果 | 課題 |
|------|---------|------|
| 日付 | 今回: 30/30 | ※別帳票での再現性は確認が必要 |
| DataNo | 今回: 30/30 | ※別帳票での再現性は確認が必要 |
| TabNo | 今回: 30/30 | ※別帳票での再現性は確認が必要 |
| **担当者名** | **完全: 22/30、部分: 7/30、失敗: 1/30** | ❌ カタカナ、数字混入、手書き崩れで誤読発生 |

**注意**: 今回のサンプルで高い精度が確認できたが、別帳票・FAX劣化・画像品質により変動する可能性あり。

**実際の誤読例:**
- 「クロダ」→ 「909」（ページ2）
- 「クロダ」→ 空白（ページ10）
- 「二宮」→ 「ニス」（ページ6）
- 実在しない名前: 「ム32」「ンビか」「石〇」「花上 = 4997」など

### なぜ正データマスタが強いか

**正データマスタ + OCR結果を組み合わせると：**

1. **完全一致候補を絞り込める**
   - OCR「ニス」 + 正データ「ニノミヤ」 → 類似度82%で候補抽出
   
2. **所属店舗で検証できる**
   - OCR「ニス」 + PDF店舗コード「AU1K0024104」 → 二宮が該当
   
3. **営業日で検証できる**
   - OCR「ニス」 + PDF日付「2026-05-17」 + 従業員有効期間 → ビンゴ
   
4. **複数候補を提示し、人間が確認できる**
   - 「候補1: 二宮（82%）/ 候補2: 西村（64%）」と提示
   - 人間が最終判断

**結果:** 「OCR 70%」→ **実務では90%以上の確度で候補補正可能**

## 🔗 照合ロジック

### 基本フロー

```
1. PDF OCR結果から「担当者名」を取得
   例：「ニス」
   
2. 正データマスタから「担当者名」で検索
   
3. 類似度を計算（複数条件で評価）
   
4. 候補を絞り込む（店舗コード、営業日など）
   
5. 候補をランキング（スコア順）
   
6. UI表示（人間が確認）
```

### 照合条件（優先度順）

#### **条件1：文字列類似度（必須）**
- OCR文字列と正データ名前の類似度を計算
- 手法：`difflib.SequenceMatcher` または `rapidfuzz`
- **スコア基準：**
  - 0.85以上: 確定候補に含める
  - 0.65～0.84: 候補に含める
  - 0.64以下: 候補除外

**例：**
```
OCR「ニス」と正データ「ニノミヤ」の類似度 = 0.67 ✓ 候補に含める
OCR「ニス」と正データ「西村」の類似度 = 0.60 ✗ 候補除外
```

#### **条件2：カナ表記との照合（重要）**
- OCR結果とカナ表記の類似度も計算
- カタカナ誤読をカバーできる

**例：**
```
OCR「ニス」とカナ「ニノミヤ」の類似度 = 0.72 → 候補昇格
```

#### **条件3：別表記・aliases との照合**
- OCR結果と aliases（昵称・別表記）で照合
- 複数の表記ゆれに対応

**例：**
```
OCR「二宮」が正データの aliases「ニノミヤ|ニノミア」に該当 → 確定
```

#### **条件4：営業日の有効期間チェック（重要）**
- PDF日付が、従業員の稼働期間内か確認
- 退職者を除外

**例：**
```
PDF日付: 2026-05-17
従業員「二宮」: active_from=2026-01-01, active_to=2099-12-31
→ 有効期間内 ✓ 候補に含める

従業員「山田」: active_from=2025-01-01, active_to=2026-03-31
→ 稼働終了（2026-03-31）なので除外 ✗
```

#### **条件5：所属店舗コードの照合**
- PDFの店舗コード（読取可能な場合）と比較
- 一致で確度UP、不一致で候補減

**例：**
```
PDF店舗コード: AU1K0024104
候補「二宮」の所属: AU1K0024104 → 一致 ✓ スコア +0.1
候補「西村」の所属: AU1K0024104 → 一致 ✓ スコア +0.1
```

#### **条件6：同一営業日に存在する候補**
- 同じ日付のデータで過去の担当者パターンを参考
- （初期版では参考情報）

#### **条件7：TabNo / DataNo との履歴照合**
- 過去の同一TabNo周辺データから候補推定
- （Phase B以降の改善）

## 📊 判定区分と表示

### **パターン1：確定候補（1人、信頼度高）**

**条件：**
- 類似度 ≥ 0.85
- 店舗コード一致
- 営業日が有効期間内
- 候補が1人だけ

**表示例：**
```
OCR担当者名: ニス
担当者候補: 二宮 (ニノミヤ)
所属店舗: 〇〇店 (AU1K0024104)
スコア: 85%
判定: 確定候補 ← 人間確認推奨（最終確認は必須）
ステータス: 確認推奨
```

**UI表示：**
```
OCR「ニス」 → 候補：二宮 / 店舗A / 85% / 確定候補 ✓
```

### **パターン2：複数候補（確度は中程度）**

**条件：**
- 類似度 0.65～0.84
- 複数の候補がある
- または店舗コード不明
- または OCR文字列が短い（2文字以下）

**表示例：**
```
OCR担当者名: ニス
候補1: 二宮 (スコア 82%)
候補2: 西村 (スコア 64%)
所属店舗: 〇〇店 (AU1K0024104)
判定: 複数候補
ステータス: 要確認
```

**UI表示：**
```
OCR「ニス」 → 候補1：二宮(82%) / 候補2：西村(64%) / 判定：要確認 ⚠️
```

### **パターン3：候補なし（データが見つからない）**

**条件：**
- OCR文字列が空白
- または 正データに近い候補がない（類似度 < 0.65）
- または 有効期間内に該当者なし

**表示例：**
```
OCR担当者名: [EMPTY]
担当者候補: なし
判定: 候補なし
ステータス: 要確認
メモ: 正データに該当候補なし。目視確認してください。
```

**UI表示：**
```
OCR「[EMPTY]」 → 候補なし / 判定：候補なし / 目視確認必要 ❌
```

### **類似度計算（Python）**

```python
from difflib import SequenceMatcher

def calc_similarity(ocr_text: str, master_text: str) -> float:
    """文字列類似度を計算"""
    matcher = SequenceMatcher(None, ocr_text, master_text)
    return matcher.ratio()

# 例
score = calc_similarity("ニス", "ニノミヤ")  # 0.67
```

## 📋 ステータス定義

| ステータス | 意味 | 処理内容 |
|----------|------|--------|
| **候補あり（確定）** | 候補が1人、スコア高 | 人間が確認して確定 |
| **複数候補** | 複数人候補あり | 人間が選択して確定 |
| **候補なし** | マスタに該当者なし | 目視確認 / 手動入力 |
| **要確認** | 候補があるが確度中程度 | 人間が確認 |
| **人間確認済み** | 最終確定済み | 次の処理へ進行 |

## 🔄 最終設計：3層構造

### **Layer 1：高精度OCR（自動確定可能）**
```
日付 / DataNo / TabNo → 100%精度で読める
↓ 自動確定
```

### **Layer 2：担当者名（候補補正 + 人間確認）**
```
OCR結果（70%） + 正データマスタ + 店舗コード + 営業日
↓ 候補候補補正
↓ UI表示（候補1, 候補2, ...）
↓ 人間が確認・確定
```

### **Layer 3：手書き・集計欄（人間確認 or 専用処理）**
```
手書き数字 / 正の字 / 集計値 → OCR単体では危険
↓ 人間確認 or Phase 6C で専用モデル導入
```

## 📌 重要な設計原則

### ❌ しないこと
- ❌ OCRで担当者を自動確定する
- ❌ OCRスコア1つだけで判定する
- ❌ 所属店舗・営業日の検証をスキップする

### ✅ すること
- ✅ OCR結果 + 正データマスタで候補補正
- ✅ 複数条件（名前、カナ、店舗、営業日）で検証
- ✅ 人間が最終確認できるUI
- ✅ ステータス管理で追跡性を確保

## 📊 設計検証

### **従来方式（OCR単体）**
```
OCR読取結果（今回サンプル担当者名）:
  - 完全成功: 22/30
  - 部分成功: 7/30
  - 読取失敗: 1/30
↓
確度: 低い（7/30が誤読・部分読取、1/30が失敗のリスク）
↓ 人間確認が必須（毎回確認負担が大きい）
```

### **提案方式（OCR + 正データマスタ）**
```
OCR読取結果: 上記と同じ
+ 正データマスタ照合（類似度計算）
+ 店舗コード検証
+ 営業日検証
↓
候補提示精度: 向上（複数候補が候補1, 2と明示される）
↓ 人間確認が容易（確定候補は1人、複数候補は絞り込み済み）
↓ 確認負担: 大幅に低減
```

**期待効果**: OCR単体より候補提示精度を高められる可能性がある
